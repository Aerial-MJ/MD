## 一、先建立层次概念：这些框架不在同一层

初学时最容易困惑的地方是：DP、DDP、FSDP、DeepSpeed、Megatron、Accelerate、TRL、verl 听起来都是"分布式训练相关"，但它们其实分属四个不同的层次，互相不是竞争关系，而是**层层叠加**的关系：

```
┌─────────────────────────────────────────────────────┐
│  第4层：你写的训练代码（应用层）                       │
└─────────────────────────────────────────────────────┘
                          ↓ 调用
┌─────────────────────────────────────────────────────┐
│  第3层：训练工具库（封装层）                           │
│   Accelerate / TRL / verl / OpenRLHF / LLaMA-Factory  │
└─────────────────────────────────────────────────────┘
                          ↓ 底层依赖
┌─────────────────────────────────────────────────────┐
│  第2层：分布式训练引擎（实现层）                       │
│   DeepSpeed / Megatron-LM / PyTorch FSDP              │
└─────────────────────────────────────────────────────┘
                          ↓ 具体实现
┌─────────────────────────────────────────────────────┐
│  第1层：分布式策略（思想层）                           │
│   DP / DDP / ZeRO / Tensor Parallel / Pipeline Parallel│
└─────────────────────────────────────────────────────┘
                          ↓ 最终依赖
┌─────────────────────────────────────────────────────┐
│                  PyTorch / CUDA / NCCL                │
└─────────────────────────────────────────────────────┘
```

一句话记忆：

```
DP/DDP/FSDP/TP/PP  →  分布式的"方法论"（怎么切）
DeepSpeed/Megatron  →  具体实现这些方法的"引擎"
Accelerate          →  让你的代码兼容多种引擎的"适配器"
TRL/verl/OpenRLHF   →  在引擎上封装 RLHF/SFT 逻辑的"工具库"
```

## 二、第 1 层：分布式策略（思想层）

### 2.1 DP（Data Parallel，数据并行）

最简单的并行方式：把数据切分给多张卡，每张卡都持有**完整的模型副本**，各自计算梯度后再汇总更新。

```
┌──────────────────────────────────────────┐
│  数据: [batch1, batch2, batch3, batch4]  │
│         ↓       ↓       ↓       ↓        │
│       GPU0    GPU1    GPU2    GPU3       │
│      [模型]  [模型]  [模型]  [模型]      │
│         ↓       ↓       ↓       ↓        │
│       梯度1   梯度2   梯度3   梯度4      │
│         └───────┴───────┴───────┘        │
│                   ↓                      │
│              汇总梯度（AllReduce）        │
│                   ↓                      │
│              更新所有卡的模型             │
└──────────────────────────────────────────┘
```

PyTorch 里的 `nn.DataParallel` 是**单进程多线程**实现，主卡承担梯度汇总和参数分发的工作，受 Python GIL 限制，多卡扩展性差，现在基本已被 DDP 取代。

**问题**：每张卡都要存完整模型，模型太大时单卡装不下，DP 就失效了。

### 2.2 DDP（Distributed Data Parallel）

DP 的升级版，PyTorch 原生支持，是目前单机/多机多卡训练的标准选择。

| 对比项 | DP | DDP |
|--------|----|----|
| 进程模型 | 单进程多线程（受 GIL 限制） | 多进程（每个 GPU 一个独立进程） |
| 通信方式 | 等所有梯度算完再汇总 | 边计算边通信（梯度计算与 AllReduce 通信 overlap） |
| 扩展性 | 差，多卡加速比低 | 好，接近线性加速 |

```
┌─────────────────────────────────┐
│  进程0(GPU0)    进程1(GPU1)      │
│  [完整模型]     [完整模型]       │
│       ↓               ↓         │
│    计算梯度         计算梯度      │
│       └───AllReduce───┘         │
│       ↓               ↓         │
│    同步更新         同步更新      │
└─────────────────────────────────┘
```

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group(backend="nccl")
model = model.to(local_rank)
model = DDP(model, device_ids=[local_rank])

for input_ids, labels in loader:
    result = model(input_ids, labels=labels)
    loss = result.loss
    loss.backward()          # backward 内部自动完成梯度 AllReduce
    optimizer.step()
    optimizer.zero_grad()
```

**限制**：每张卡仍需存完整的参数 + 梯度 + 优化器状态，适合"模型能放进单卡显存"的场景；一旦模型规模超过单卡显存，DDP 本身无法解决，需要引入下面的显存分片方案。

### 2.3 FSDP / ZeRO（显存分片，DP 的显存优化版）

**核心问题**：DDP 中每张卡都存一份完整的参数、梯度、优化器状态，这是严重的冗余。

**核心思想**：把参数、梯度、优化器状态**切碎分散**到各张卡上，需要计算时再临时通信拼出完整数据，用完立刻释放。

```
┌──────────────────────────────────────────┐
│  DDP（每卡存完整模型）：                   │
│  GPU0: [全部参数][全部梯度][全部优化器]    │
│  GPU1: [全部参数][全部梯度][全部优化器]    │
│  GPU2: [全部参数][全部梯度][全部优化器]    │
│  → 严重冗余！                             │
│                                           │
│  FSDP/ZeRO（切片存储）：                  │
│  GPU0: [参数1/3][梯度1/3][优化器1/3]      │
│  GPU1: [参数2/3][梯度2/3][优化器2/3]      │
│  GPU2: [参数3/3][梯度3/3][优化器3/3]      │
│  → 显存大幅减少！                         │
│                                           │
│  需要计算时：临时 AllGather 拼完整参数     │
│  计算完立刻释放                           │
└──────────────────────────────────────────┘
```

- **ZeRO** 是 DeepSpeed（微软）提出的思想，**FSDP（Fully Sharded Data Parallel）是 PyTorch 官方原生实现，思想上等价于 ZeRO-3**。
- 优点：可以训练远超单卡显存的大模型；缺点：通信开销比纯 DDP 更大。
- ZeRO 三个阶段的具体切分方式和显存节省的精确计算，见 [四、ZeRO 三阶段深度详解](#四zero-三阶段深度详解显存到底怎么切的)。

### 2.4 Tensor Parallel（张量并行，TP）：MLP 与 Attention 具体怎么切

把模型**权重矩阵本身**切开，多张卡各算一部分，最后合并结果。

```
┌─────────────────────────────────┐
│  一个 Linear 层 W [4096 × 4096] │
│                                 │
│  GPU0: W 的左半部分 [4096×2048] │
│  GPU1: W 的右半部分 [4096×2048] │
│                                 │
│  计算时各自算一半，再合并结果    │
└─────────────────────────────────┘
```

适合场景：单层矩阵本身就大到一张卡放不下（或算力不够）；是 Megatron-LM 的核心技术。ZeRO 解决的是"参数、梯度、优化器状态"的显存分片问题，但每次前向/反向仍然是完整的矩阵计算；张量并行则是把矩阵计算本身也拆开。**目标**：切分之后各卡尽量独立计算，通信（跨卡同步）越少越好，因为通信是分布式训练里最慢的瓶颈。

#### 2.4.1 MLP 层怎么切：为什么必须"先列切、后行切"

FFN/MLP 层的计算可以简化为两层线性变换夹一个非线性激活函数：

```
MLP 数据流：
X（输入） → A（第一层线性） → GELU（非线性激活） → B（第二层线性） → Y（输出）

公式：Y = GELU(X @ A) @ B
```

要把 `A`、`B` 这两个大矩阵切到多卡上，无非两种切法：**列切**（按输出维度切）或**行切**（按输入维度切）。关键问题是：先切的第一层 `A` 到底该列切还是行切？

**第一层 A 必须列切：因为 GELU 是非线性的**

`GELU` 满足**先加再激活 ≠ 先激活再加**，即：

```
GELU(a1 + a2) ≠ GELU(a1) + GELU(a2)      非线性，不能拆开算
```

这决定了 `A` 只能列切，不能行切：

| 切法 | 每卡计算出的中间结果 | 能否直接过 GELU |
|------|---------------------|-----------------|
| ❌ 行切 A（按输入维度切，每卡拿一部分 X 的列） | 每卡只能算出对最终结果的"部分和" | 不能，必须先 AllReduce 把部分和加起来，再过 GELU（多一次通信） |
| ✅ 列切 A（按输出维度切，每卡拿完整的 X，算出输出的一部分列） | 每卡得到的是"完整的列"，即最终结果里独立的几列 | 可以，GELU 是逐元素运算，每一列互不影响，各卡直接独立算，0 通信 |

```
所以 A 必须列切，才能让 GELU 在各卡上独立计算，不需要任何通信
```

**第二层 B 只能行切：正好接住 A 列切后的输出**

`A` 列切之后，每张卡上 `GELU(X @ A_i)` 输出的是结果矩阵按列分块的一部分；要接住这些列分块，`B` 必须按对应的行切分，这样每张卡才能维度对齐做矩阵乘法：

```
GPU1: X → A1（列切）→ GELU → B1（行切）→ 部分积
GPU2: X → A2（列切）→ GELU → B2（行切）→ 部分积
                                  ↓
                    AllReduce 求和 → Y（最终输出）
```

`B` 行切后，每张卡算出来的只是最终输出 `Y` 的"部分和"（因为每张卡只贡献了完整求和链路里的一部分维度），所以最后必须做**一次 AllReduce** 把各卡的部分积加起来，才能得到正确的 `Y`。

**为什么是"先列切、后行切"而不是反过来**

| 切分方案 | 通信次数 | 原因 |
|---------|---------|------|
| ✅ 先列切 A、后行切 B（标准做法） | **1 次 AllReduce**（只在最后求和） | GELU 前各卡独立、互不依赖，只需在两层线性变换算完后同步一次 |
| ❌ 先行切 A | **2 次通信**（GELU 前一次 AllReduce，末尾还要一次） | 行切 A 得到的是部分和，必须先同步才能过 GELU，之后 B 还要再同步一次，通信量翻倍 |

一句话总结：**关键在于 GELU 非线性不能作用在"部分和"上，只能作用在"完整的列"上，所以第一层必须列切，让非线性激活各卡独立算；第二层顺势行切接住列分块，最后只需一次 AllReduce 收尾。**

#### 2.4.2 Self-Attention 层怎么切：同样是先列切、后行切

Attention 层的切分遵循同样的"先列切、后行切"套路，而且**不是"先行切再列切"反过来的做法**——切分顺序和 2.4.1 节的 MLP 完全一致：

```
Q/K/V 投影矩阵：按注意力头（head）列切 → 每张卡负责若干个头，头与头之间计算完全独立，0 通信
输出投影 W_O：行切 → 接住多头拼接后的列分块，最后一次 AllReduce 收尾
```

**举一个具体的小例子**：假设 hidden=8，有 4 个注意力头（每头 head_dim=2），4 张卡，一个 Self-Attention 层有 $W_Q, W_K, W_V$（生成 Q/K/V）和 $W_O$（多头拼接后的输出投影）：

```
第一步（列切，且按 head 对齐）：
W_Q（8×8矩阵）按列切成4份，每份2列，正好对应1个注意力头：
  GPU0: W_Q 的第1~2列 → 对应 Head1
  GPU1: W_Q 的第3~4列 → 对应 Head2
  GPU2: W_Q 的第5~6列 → 对应 Head3
  GPU3: W_Q 的第7~8列 → 对应 Head4
W_K、W_V 同样按列切，切法完全对齐（GPU0 拿 W_K/W_V 里对应 Head1 的那几列）
```

跟 MLP 里"列切之后接 GELU 不用通信"是同一个原理：**每个头的注意力计算（$QK^T$、softmax、再乘 $V$）都只依赖这个头自己的 Q/K/V，跟别的头完全无关**：

```
GPU0: 只用自己的 Q1,K1,V1 独立算出 Head1 的完整注意力输出（QKᵀ/softmax/*V 全部本地完成）
GPU1: 只用自己的 Q2,K2,V2 独立算出 Head2 的完整注意力输出
GPU2、GPU3 同理

这一整套 Attention 核心计算（包括 softmax）全程 0 通信！
MLP：列切让每一列的 GELU 互不依赖
Attention：列切（按head）让每个头的整套注意力计算互不依赖
```

这也解释了为什么"多头注意力"这个设计天生就特别适合张量并行——头与头之间在数学上本来就是并行、独立的，TP 只是顺势把这种"天然并行"映射到物理上的多张卡。

```
第二步（行切，接住多头拼接结果）：
GPU0算出 Head1输出（长度2）  GPU1算出 Head2输出（长度2）
GPU2算出 Head3输出（长度2）  GPU3算出 Head4输出（长度2）
拼起来 = 长度8的完整向量，但这4段分别"躺在"4张不同的卡上，没人有完整拼接结果

W_O（8×8矩阵）要把这个长度8的向量变换成输出，所以 W_O 必须按行切成4份：
  GPU0拿W_O第1~2行 ← 对应Head1输出那一段    GPU1拿W_O第3~4行 ← 对应Head2输出那一段
  GPU2拿W_O第5~6行 ← 对应Head3输出那一段    GPU3拿W_O第7~8行 ← 对应Head4输出那一段

每张卡：自己的 Head_i输出 @ W_O对应行 = 部分和_i（不是最终结果，只是贡献的一部分）
真正的输出 = 部分和0+部分和1+部分和2+部分和3 → 必须 AllReduce 才能凑出正确、完整的结果
```

一张图对照 MLP 和 Attention，两者结构完全对称：

```
MLP:        X --列切A--> GELU(独立算) --行切B--> 部分和 --AllReduce--> Y
Attention:  X --列切WQKV(按head)--> 每头独立算attention --行切W_O--> 部分和 --AllReduce--> 输出

第一层矩阵：列切，让"非线性/头内计算"各卡独立、0通信
第二层矩阵：行切，接住列切分块，最后1次AllReduce收尾
```

如果反过来"先行切 $W_Q$"：每张卡只能拿到不完整的 Q（缺了一部分 hidden 维度），根本没法独立算出一个头的注意力，必须先 AllReduce 凑出完整的 Q 才能继续，通信次数直接翻倍——这就是为什么切分顺序不能颠倒。

标准套路：**先列切、后行切**，全程只需 1 次 AllReduce，这也是 Megatron-LM 等张量并行框架里 MLP 和 Self-Attention 层的通用切分方式。

> 关联笔记：GELU 等激活函数的原理见 [激活函数和损失函数](../深度学习/激活函数和损失函数.md)；`W_Q/W_K/W_V/W_O` 等权重矩阵的形状定义见 [Transformer向量与参数详解](../深度学习/Transformer向量与参数详解.md)；MLP 张量并行在 MiniMind 训练脚本里的上下文（何时该从 ZeRO 升级到 TP）见 [MiniMind从0到1构建大模型 · 4.5.4](MiniMind从0到1构建大模型.md#454-张量并行mlp-层如何切分到多卡)。

### 2.5 Pipeline Parallel（流水线并行，PP）

把模型**按层切开**，不同卡负责不同的连续层段，数据像流水线一样依次流过各卡。

```
┌─────────────────────────────────┐
│  GPU0: Layer 1-8   （前8层）    │
│  GPU1: Layer 9-16  （中8层）    │
│  GPU2: Layer 17-24 （后8层）    │
│                                 │
│  数据像流水线一样流过各卡        │
└─────────────────────────────────┘
```

**核心问题：Bubble（气泡/GPU 空转）**。因为各阶段必须串行等待上一阶段的输出，朴素实现会导致大量 GPU 时间浪费在等待上。这是流水线并行最大的痛点，详见 [六、流水线并行的 Bubble 问题详解](#六流水线并行的-bubble-问题详解)。

### 2.6 Sequence Parallel（序列并行，SP，补充）

`test.txt` 的层次图中提到了 SP 但未展开，这里补充：序列并行是 Megatron-LM 后续引入的优化，把 **LayerNorm、Dropout 等激活值沿序列维度切分**到各张卡（这些操作在 batch/seq 维度上是逐元素独立的，不需要像 Attention/MLP 那样做张量并行的矩阵切分），进一步降低张量并行区域内的激活值显存占用，通常和 TP 配合使用（合称 TP+SP）。

## 三、第 2 层：分布式训练引擎（实现层）

### 3.1 DeepSpeed（微软）

核心贡献是 **ZeRO（Zero Redundancy Optimizer）**，此外还提供：

- **ZeRO-Offload**：把参数/优化器状态卸载到 CPU/NVMe，让单卡也能训练远超显存容量的模型
- 混合精度训练（FP16/BF16）
- 梯度累积、激活检查点（Activation Checkpointing）

使用方式是写一个 `ds_config.json` 配置文件，几乎不改动训练代码：

```json
{
  "train_micro_batch_size_per_gpu": 8,
  "gradient_accumulation_steps": 4,
  "bf16": {"enabled": true},
  "zero_optimization": {
    "stage": 2,
    "allgather_bucket_size": 2e8,
    "reduce_bucket_size": 2e8
  }
}
```

```python
import deepspeed

model_engine, optimizer, loader, scheduler = deepspeed.initialize(
    model=model, optimizer=optimizer, training_data=dataset, config="ds_config.json"
)

for batch in loader:
    loss = model_engine(batch).loss
    model_engine.backward(loss)   # 梯度分片同步在内部自动处理
    model_engine.step()
```

### 3.2 Megatron-LM（英伟达）

核心贡献是 **3D 并行**：Tensor Parallel + Pipeline Parallel + Data Parallel 三种并行方式组合使用，可以训练千亿/万亿参数级别的模型。

```
┌──────────────────────────────────────────┐
│           Megatron 3D 并行                │
│                                           │
│  Tensor Parallel  → 切权重矩阵            │
│  Pipeline Parallel → 切模型层             │
│  Data Parallel    → 切数据                │
│                                           │
│  三种并行组合使用                          │
│  可以训练万亿参数模型                      │
└──────────────────────────────────────────┘
```

特点：专为超大模型设计（GPT-3 级别）；与 NVIDIA 硬件深度绑定；代码侵入性强（需要改模型代码，把标准 `nn.Linear` 替换成 Megatron 提供的 `ColumnParallelLinear`/`RowParallelLinear` 等）；性能极致但使用门槛高。

### 3.3 DeepSpeed vs Megatron

| | DeepSpeed | Megatron-LM |
|---|-----------|--------------|
| 核心技术 | ZeRO 显存优化 | 3D 并行 |
| 使用难度 | 中等 | 高 |
| 代码侵入性 | 低 | 高 |
| 适合规模 | 10B 以下更常见 | 100B+ |
| 典型用户 | 普通研究者、中小团队 | 大厂预训练基础模型 |
| 开发者 | 微软 | 英伟达 |

现实中很多大厂采用 **Megatron-DeepSpeed** 结合方案：3D 并行负责切分模型和数据，ZeRO 负责进一步压缩每张卡上的显存占用，两者并不冲突，可以叠加使用（比如在 DP 维度上应用 ZeRO）。

### 3.4 PyTorch FSDP

PyTorch 官方原生实现，思想上是 ZeRO-3 的原生复刻（参数、梯度、优化器状态都切分），不需要额外安装 DeepSpeed，和 PyTorch 生态（`torch.compile` 等）集成更紧密，是目前 HuggingFace Accelerate/TRL 默认推荐的多卡方案之一。

## 四、ZeRO 三阶段深度详解：显存到底怎么切的

### 4.1 先回答两个常见疑问

**Q1：ZeRO 的切分是在 DP 基础上做的吗？**

是的。ZeRO 本质上**仍然是数据并行（DP）**——每张卡处理不同的数据分片，模型的计算逻辑不变。ZeRO 改变的只是"参数、梯度、优化器状态"这几类模型状态在多卡间**如何存储**，而不是引入新的并行计算方式。

**Q2：单卡也能用 DeepSpeed，那切分还有意义吗？**

单卡上 ZeRO 的"切分到多卡"没有意义（因为只有 1 张卡）。单卡使用 DeepSpeed 主要是为了用它的其他能力：混合精度训练、梯度累积、激活检查点，以及最重要的 **ZeRO-Offload**（把优化器状态/参数卸载到 CPU 内存甚至 NVMe 硬盘，用较慢的存储换取能训练更大的模型）。

### 4.2 训练时显存里到底存了什么

以参数量为 $\Psi$ 的模型、混合精度训练（FP16/BF16 计算 + FP32 优化器状态）、Adam 优化器为例：

| 显存占用项 | 大小（bytes） | 说明 |
|-----------|--------------|------|
| 模型参数（FP16/BF16） | $2\Psi$ | 前向/反向计算使用 |
| 梯度（FP16/BF16） | $2\Psi$ | 反向传播产生 |
| 优化器状态（FP32）— 最大头 | $12\Psi$ | FP32 主参数 $4\Psi$ + 一阶动量 $4\Psi$ + 二阶动量 $4\Psi$ |
| **合计（不含激活值）** | **$16\Psi$** | 7B 模型 → 约 112GB，单张 A100(80GB) 装不下 |

> 这里的精确数值和更细的正反梯度峰值分析（比如是否需要额外的 FP32 梯度副本导致 $18\Psi/20\Psi$）见 [LLM 大模型训练-推理显存占用分析](../../论文/docs/大模型/LLM%20大模型训练-推理显存占用分析.md)，本节只关注 ZeRO 切分的相对节省比例。

普通 DP（未使用 ZeRO）下，**N 张卡每张都存一份完整的 $16\Psi$**，总显存是 $16\Psi \times N$，其中有效信息只有 $16\Psi$，冗余比例是 $(N-1)/N$。

### 4.3 ZeRO-1：只切优化器状态

把 $12\Psi$ 的优化器状态平均切成 $N$ 份，每张卡只存 $1/N$：

```
每卡显存 = 2Ψ（完整参数） + 2Ψ（完整梯度） + 12Ψ/N（优化器状态分片）
```

以 $N=4$ 为例：每卡显存 $= 2\Psi + 2\Psi + 3\Psi = 7\Psi$（相比 DP 的 $16\Psi$，节省约 2.3×）。

训练流程：
```
前向传播：各卡用自己完整的参数正常计算（参数还是完整的，没切）
反向传播：各卡算出完整梯度，AllReduce 同步梯度（和普通 DP 一样）
参数更新：← 这里不一样了！
  每张卡只用自己存的那 1/N 优化器状态，更新对应的 1/N 参数
  更新完后，AllGather 把各卡更新的参数分片广播给所有人
  → 所有卡重新拥有完整参数
```

### 4.4 ZeRO-2：切优化器状态 + 梯度

在 ZeRO-1 基础上，梯度也切分：

```
每卡显存 = 2Ψ（完整参数） + 2Ψ/N（梯度分片） + 12Ψ/N（优化器状态分片）
```

以 $N=4$ 为例：每卡显存 $= 2\Psi + 0.5\Psi + 3\Psi = 5.5\Psi$（相比 DP 节省约 2.9×）。

训练流程的关键变化：反向传播不再用 AllReduce 同步完整梯度，而是用 **Reduce-Scatter**（求和后按分片切给各卡，每卡只保留自己负责的那一段梯度求和结果，其余立刻释放）。

**为什么用 Reduce-Scatter 而不是 AllReduce？**

```
AllReduce = Reduce-Scatter + AllGather

普通 DP： Reduce-Scatter（汇总梯度） + AllGather（广播回完整梯度）
         = 每张卡都有完整梯度

ZeRO-2：  只做 Reduce-Scatter 这一步！
         每卡只保留自己负责的梯度分片
         省掉了 AllGather 这一步 → 梯度显存直接减少 N 倍
```

### 4.5 ZeRO-3（≈ FSDP）：切优化器状态 + 梯度 + 参数

连参数也切分，三类状态全部按 $1/N$ 分片存储：

```
每卡显存 = 2Ψ/N（参数分片） + 2Ψ/N（梯度分片） + 12Ψ/N（优化器状态分片）
        = 16Ψ / N
```

以 $N=4$ 为例：每卡显存 $= 16\Psi/4 = 4\Psi$（相比 DP 节省 4×）；$N=64$ 时理论可降到约 $0.25\Psi$（节省 64×）——**这也是为什么会看到"ZeRO-3 理论节省 64×"这种说法：它对应的是 $N=64$ 张卡这个特定场景，倍数会随卡数 $N$ 线性提升，并不是一个固定值**，套用时要注意带上具体的 $N$。

训练流程最复杂，因为每一层计算时都需要该层的**完整**参数：

```
前向传播：
  计算 Layer k 之前：AllGather 出 Layer k 的完整参数
  所有卡用完整参数计算 Layer k
  计算完立刻丢掉其他卡的参数分片！只保留自己负责的 1/N
  继续下一层，重复上述过程

反向传播：
  同样需要 AllGather 参数（算梯度需要参数）
  算完梯度后 Reduce-Scatter，每卡只保留自己负责的梯度分片

参数更新：
  各卡独立更新自己负责的参数分片，不需要 AllGather
  （下一次前向时再按需重新 AllGather）
```

### 4.6 三阶段完整对比

| | 优化器状态 | 梯度 | 参数 | 通信操作 | 每卡显存（$N$ 卡） |
|---|-----------|------|------|---------|-------------------|
| 普通 DP | 完整副本 | 完整副本 | 完整副本 | AllReduce | $16\Psi$ |
| ZeRO-1 | 切分 $1/N$ | 完整副本 | 完整副本 | AllReduce + AllGather | $4\Psi + 12\Psi/N$ |
| ZeRO-2 | 切分 $1/N$ | 切分 $1/N$ | 完整副本 | Reduce-Scatter + AllGather | $2\Psi + 14\Psi/N$ |
| ZeRO-3（≈FSDP） | 切分 $1/N$ | 切分 $1/N$ | 切分 $1/N$ | AllGather（按需）+ Reduce-Scatter | $16\Psi/N$ |

> 表中公式是显存占用的通用表达式（$N$ 是任意卡数），代入 $N=4$ 就是本节推导的 $7\Psi/5.5\Psi/4\Psi$。切勿把某个具体 $N$ 下算出的倍数（如"4×/8×/64×"）当成与卡数无关的固定值。

### 4.7 ZeRO-Offload：为什么单卡也能用 DeepSpeed

单卡用 ZeRO 没有"切分给多卡"的意义，但可以用 **ZeRO-Offload**：把显存压力转移到更大但更慢的存储介质（CPU 内存或 NVMe 硬盘）。

```
┌─────────────────────────────────────────┐
│  GPU 显存（快但小）：                     │
│    参数（FP16）  ← 计算时在 GPU          │
│    梯度（FP16）  ← 计算时在 GPU          │
│                                          │
│  CPU 内存（慢但大）：                     │
│    优化器状态（FP32） ← 卸载到 CPU       │
│    FP32 主参数        ← 卸载到 CPU       │
│                                          │
│  流程：GPU 算梯度 → 传给 CPU → CPU 更新参数 → 传回 GPU 继续训练 │
└─────────────────────────────────────────┘
```

效果：单卡 24GB 显存也可能训练原本需要 80GB 显存的模型；代价是 CPU-GPU 之间的数据传输会引入额外延迟，训练速度会变慢。

## 五、手把手实例：用一个具体模型把 DP→ZeRO→TP/PP→框架 全部串起来

前面几节把每种并行策略、每个框架分开讲清楚了，但初学时最容易卡壳的地方是：**通信到底是怎么"凭空产生"的？** 这一节固定一个"麻雀虽小五脏俱全"的小模型，用具体数字把 DP、DDP、ZeRO-1/2/3、FSDP、TP、PP 串成一条完整故事线，再把 DeepSpeed/Megatron/Accelerate/TRL 这些框架安放到故事线里的对应位置。

### 5.1 先固定一个方便心算的模型

不用真实的几十亿参数模型，就用一个假想的 2 层小模型：

```
一个超小的语言模型：
  Layer 1（一个 Block）：参数 100 个
  Layer 2（一个 Block）：参数 100 个
  总参数量 Ψ = 200 个

用 4 张卡训练（GPU0, GPU1, GPU2, GPU3）
用 Adam 优化器（需要维护一阶动量 m 和二阶动量 v）
```

先记住一个铁律（后面反复会用到），Adam 优化器下每个参数需要存 4 份东西：

```
① 参数本身（fp16，2字节）        ← 前向计算用
② 梯度（fp16，2字节）             ← 反向传播产生
③ fp32 主参数副本（4字节）        ← 混合精度训练里为了更新精度而保留（见 4.2 节）
④ Adam 一阶动量 m（fp32，4字节）  ← "过去梯度的移动平均"
⑤ Adam 二阶动量 v（fp32，4字节）  ← "过去梯度平方的移动平均"

一共 2+2+4+4+4 = 16 字节/参数（即 4.2 节里 16Ψ 的由来），这个例子里 16Ψ = 16×200 = 3200 字节
```

### 5.2 第一站：DP / DDP —— 数据不同，但每张卡的"东西"都一模一样

```
GPU0: 200个参数[完整] + 200个梯度[完整] + Adam状态[完整]  ← 一整套
GPU1: 200个参数[完整] + 200个梯度[完整] + Adam状态[完整]  ← 一整套（一模一样的副本）
GPU2: 200个参数[完整] + 200个梯度[完整] + Adam状态[完整]  ← 一整套（一模一样的副本）
GPU3: 200个参数[完整] + 200个梯度[完整] + Adam状态[完整]  ← 一整套（一模一样的副本）
```

每一步训练具体发生了什么：

```
1. 4张卡拿到不同的数据（比如4个不同的句子）
2. 各自独立做完整的 forward + backward
   → GPU0 算出梯度 g0（200个数）
   → GPU1 算出梯度 g1（200个数）
   → GPU2 算出梯度 g2（200个数）
   → GPU3 算出梯度 g3（200个数）
   （注意：这4份梯度，因为输入数据不同，数值是不一样的！）

3. ★ 这里必须做一次通信，把4份不同的梯度"统一成一份"，否则4张卡各自按自己的梯度更新，
     4张卡的模型会越训越不一样，训练直接崩掉。

   用的通信操作是 AllReduce：
   AllReduce(g0, g1, g2, g3) = 求平均 → g_avg（200个数）
   通信完，4张卡手里都拿到同一份 g_avg

4. 4张卡各自用同一份 g_avg，各自更新自己那份完整的参数
   → 更新完，4张卡的参数又变得完全一样了
```

**这就是"通信是怎么产生的"最本质的答案**：每张卡看到的数据不同、算出的梯度不同，必须靠通信把梯度"拉齐"，否则多卡训练出来的是 4 个不同的模型，而不是 1 个模型被训练了 4 倍的数据。

DDP 相比 DP 只是把这个 AllReduce 做得更聪明：DP 是等全部 200 个参数的梯度都算完才通信一次；DDP 是反向传播算到 Layer 2 的梯度就先通信 Layer 2 的梯度（不用等 Layer 1 也算完），一边算 Layer 1 的梯度、一边同步 Layer 2 的梯度，两件事重叠（overlap），省时间。**通信的"内容"没变，变的是"时机"**。

DP/DDP 的问题很直白：每张卡都要存 $16\Psi = 16\times200 = 3200$ 字节的"一整套东西"，4 张卡总共存了 $4\times3200=12800$ 字节，但里面真正有用的信息只有 3200 字节（因为 4 份都一样），剩下 9600 字节全是重复的废料。模型一旦大到一张卡装不下，DP/DDP 就没救了——这正是 4.3~4.5 节 ZeRO 三阶段要解决的问题，下面用同一个例子把切分过程具象化。

### 5.3 第二站：ZeRO-1 —— 只把"优化器状态"这坨最大的废料切开

回顾一下 $16\Psi$ 里各部分占比：

```
② 梯度：2字节/参数      （小头）
①③ 参数：2+4=6字节/参数  （中头）
④⑤ Adam动量：4+4=8字节/参数（最大头！）
+ ③里的fp32主参数：4字节（这个通常和优化器状态算在一起，一共12Ψ）
```

ZeRO-1 的想法：既然每张卡各自更新参数时用的是同一份 `g_avg`，那为什么每张卡都要自己重复算一遍"用 Adam 公式更新全部 200 个参数"这个动作？让每张卡只负责更新其中 50 个参数就够了！

```
GPU0 负责更新参数 [1~50]，只存这50个参数对应的 Adam 状态
GPU1 负责更新参数 [51~100]，只存这50个参数对应的 Adam 状态
GPU2 负责更新参数 [101~150]，只存这50个参数对应的 Adam 状态
GPU3 负责更新参数 [151~200]，只存这50个参数对应的 Adam 状态

但是！参数和梯度，每张卡还是存完整的200个（没切）
```

具体流程（对照 5.2 节的 4 步，只有第 4 步变了）：

```
1. 4张卡各自算完整的 forward+backward（和之前一样）
2. 得到4份不同的梯度 g0,g1,g2,g3（各200个数）
3. AllReduce 得到 g_avg（200个数，每张卡都有完整的一份，和之前一样）
4. ★ 变化在这里：
   GPU0：只用 g_avg 里第[1~50]段，配合自己存的这50个参数的 Adam 状态，更新参数[1~50]
   GPU1：只用 g_avg 里第[51~100]段，更新参数[51~100]
   GPU2：只用 g_avg 里第[101~150]段，更新参数[101~150]
   GPU3：只用 g_avg 里第[151~200]段，更新参数[151~200]

   更新完之后：GPU0 手里的参数[1~50]是最新的，但[51~200]还是旧的！

5. ★ 多一步通信：AllGather，把4张卡刚更新完的那一小段参数，广播给所有人
   GPU0: 广播出去 参数[1~50]（刚更新的）
   GPU1: 广播出去 参数[51~100]（刚更新的）
   GPU2: 广播出去 参数[101~150]（刚更新的）
   GPU3: 广播出去 参数[151~200]（刚更新的）

   AllGather 之后，4张卡都重新拿到完整的、最新的200个参数
```

省了什么：每张卡的 Adam 状态从"存 200 个参数的"变成"只存 50 个参数的"，这部分（$12\Psi$ 那一大块）直接变成 1/4。代价：多了一次 AllGather 通信。

### 5.4 第三站：ZeRO-2 —— 连梯度也切开，用 Reduce-Scatter 代替 AllReduce

ZeRO-1 里，第 3 步的 AllReduce 其实是浪费的：每张卡先辛辛苦苦求出完整的 200 个数的 `g_avg`，但第 4 步每张卡其实只用得上自己负责的那 50 个数，剩下 150 个数白白占了显存。

ZeRO-2 的想法：既然反正只用得上一部分，那干脆不要"先求完整平均、再广播"，而是"边求平均边直接分片"——这就是 **Reduce-Scatter**（对照 6.3 节 `AllReduce = Reduce-Scatter + AllGather` 的拆解）：

```
普通 DDP/ZeRO-1 走的是完整的 AllReduce（Reduce-Scatter + AllGather 两步都做）

ZeRO-2 只做第一步 Reduce-Scatter，第二步不做：

GPU0原始梯度[1~50][51~100][101~150][151~200]  ┐
GPU1原始梯度[1~50][51~100][101~150][151~200]  ├─ Reduce-Scatter ─┐
GPU2原始梯度[1~50][51~100][101~150][151~200]  ┤                  │
GPU3原始梯度[1~50][51~100][101~150][151~200]  ┘                  │
                                                                  ↓
GPU0：只拿到 [1~50]段 的4卡平均值      ← 只存这一段，其余段的梯度立刻释放！
GPU1：只拿到 [51~100]段 的4卡平均值
GPU2：只拿到 [101~150]段 的4卡平均值
GPU3：只拿到 [151~200]段 的4卡平均值
```

之后的更新步骤和 ZeRO-1 一样（各卡更新自己那 50 个参数，再 AllGather 拿回完整参数）。

省了什么：梯度显存从"每卡存完整 200 个"变成"每卡只存 50 个"，梯度这部分（$2\Psi$ 那一块）也变成 1/4。通信量反而没有增加（Reduce-Scatter 的通信量本来就和 AllReduce 差不多，只是没有再做后面的 AllGather 那一半）。

### 5.5 第四站：ZeRO-3（≈ FSDP）—— 连参数本身也不完整存了，最激进

前两站，"参数"这块（$2\Psi$）一直是每张卡都存完整 200 个的。ZeRO-3 问：参数是不是也能切？

```
GPU0: 只存参数 [1~50]
GPU1: 只存参数 [51~100]
GPU2: 只存参数 [101~150]
GPU3: 只存参数 [151~200]

（没有任何一张卡，手里有完整的200个参数！）
```

问题来了：算 Layer 1 的 forward 时，需要用到 Layer 1 完整的权重矩阵，不能只用其中 1/4。所以：

```
1. 要算 Layer 1 之前，先做一次 AllGather，临时把 Layer 1 完整的参数拼出来
   （4张卡各自贡献自己存的那一份，拼成一份完整的、每张卡都有）
2. 4张卡各自用这份"临时拼出来的完整参数"，算各自数据的 forward
3. ★ 算完立刻把"临时拼出来的、不是自己负责的那部分参数"扔掉！
   GPU0：只留下自己原本负责的 [1~50]，[51~200] 部分用完就删
4. 继续算 Layer 2，重复"AllGather拼参数 → 算 → 用完就删"
5. backward 也是一样：算梯度前先 AllGather 拼参数，算完梯度后 Reduce-Scatter 切梯度
6. 参数更新：每张卡只更新自己负责的那一份，不需要再额外通信
```

代价很直白：原来 DP 只需要一次 AllReduce 通信；ZeRO-3 变成每一层都要 AllGather（拼参数）+ 每一层都要 Reduce-Scatter（切梯度），通信次数大幅增加，换来的是显存降到 $16\Psi/N$（这个例子里就是 $3200/4=800$ 字节/卡，是 DP 的 1/4）。

FSDP 就是 PyTorch 官方把这一整套"ZeRO-3 式的切法"原生实现了一遍，用法上会自动帮你在每一层前后插入 AllGather/Reduce-Scatter，不需要你手写。

### 5.6 一张总表把这个例子的数字串起来（N=4 张卡，Ψ=200 参数）

| 阶段 | 每卡存参数 | 每卡存梯度 | 每卡存优化器状态 | 每卡总显存（字节） | 通信操作 |
|------|-----------|-----------|-----------------|-------------------|---------|
| DP/DDP | 200个(完整) | 200个(完整) | 200份(完整) | $16\times200=3200$ | AllReduce |
| ZeRO-1 | 200个(完整) | 200个(完整) | 50份(切1/4) | $2\times200+2\times200+12\times50=1400$ | AllReduce + AllGather |
| ZeRO-2 | 200个(完整) | 50个(切1/4) | 50份(切1/4) | $2\times200+2\times50+12\times50=1100$ | Reduce-Scatter + AllGather |
| ZeRO-3/FSDP | 50个(切1/4) | 50个(切1/4) | 50份(切1/4) | $16\times50=800$ | 每层 AllGather + Reduce-Scatter |

**一句话总结这条主线**：通信的产生根源，就是"多张卡各自算出来的东西不一样，必须同步"；从 DP 到 ZeRO-3，故事其实是同一件事——用更多、更细粒度的通信，换取更少的显存冗余，越往后显存越省，但通信次数和复杂度也越高。

### 5.7 加入 TP：把"一层"拆开算

上面 DP 系列从头到尾切的都是同一个东西：**数据**。模型本身（200 个参数、2 层）从来没被拆开过，只是"存储这些参数/梯度/优化器状态的方式"从"每卡一份完整的"变成"切成 4 份"：

```
DP系列的核心不变量：
  每张卡看到的模型，永远是"逻辑上完整的2层模型"
  （哪怕 ZeRO-3 把参数物理上切到4张卡，用之前也会先 AllGather 拼回完整的）
  变的只是：不同的卡，拿到不同的数据（句子）
```

TP 和 PP 解决的是完全不同的问题：如果这个模型不是 200 个参数，而是大到一张卡根本装不下（哪怕只装 1/4 也装不下，因为单层矩阵本身就太大），DP 系列的"切存储方式"就不够用了，必须把模型的**计算本身**也拆开。

#### 5.7.1 先看最简单的情况：只有一层矩阵，列切之后互不依赖

为了能真正心算，把 Layer 1 换成一个具体的、只有 $4\times4$ 的小矩阵（真实场景里可能是 $4096\times4096$，原理完全一样），输入 $X$ 是 1 个 token 的向量（长度 4）：

```
输入 X（1个token，长度4）：  X = [x1, x2, x3, x4]

权重 W（4×4矩阵，即Layer1）：
        列1  列2  列3  列4
行1  [  w11  w12  w13  w14 ]
行2  [  w21  w22  w23  w24 ]
行3  [  w31  w32  w33  w34 ]
行4  [  w41  w42  w43  w44 ]

要算：Y = X @ W，Y 是长度4的向量，Y 的第 j 个元素 = X 和 W 第 j 列做点积
     Y_j = x1*w1j + x2*w2j + x3*w3j + x4*w4j
```

TP 把 $W$ **按列**切成 4 份，每张卡拿完整的一整列（4 个数）：

```
GPU0 拿列1: [w11,w21,w31,w41]     GPU1 拿列2: [w12,w22,w32,w42]
GPU2 拿列3: [w13,w23,w33,w43]     GPU3 拿列4: [w14,w24,w34,w44]

注意关键区别：4张卡处理的是同一个句子的同一份输入 X（不是4个不同的句子！）
每张卡各自算：
  GPU0: Y_1 = x1*w11+x2*w21+x3*w31+x4*w41   ← Y 的第1个数，完整、正确，不依赖其他卡
  GPU1: Y_2 = x1*w12+x2*w22+x3*w32+x4*w42   ← Y 的第2个数
  GPU2: Y_3 = ...同理...
  GPU3: Y_4 = ...同理...

这一步完全不需要通信！因为 X 每张卡都有完整的一份（复制），
W 按列切开后，算某一列的点积不需要用到别的列的数据，四张卡互不打扰
```

算完之后，$Y = [Y_1, Y_2, Y_3, Y_4]$ 这个完整向量"分散"存在 4 张卡上，每张卡只知道自己那一个数。如果 $Y$ 要经过 GELU 这种**逐元素**的激活函数，也完全不需要通信——因为 `GELU(Y_1)` 只需要 `Y_1` 自己，GPU0 直接就地算，其余同理。

#### 5.7.2 接上第二层（行切）：为什么这时候必须通信

真实的 MLP 不会只有一层，紧接着还有第二层矩阵 $B$（对应 2.4.1 节的"先列切、后行切"）。这次把 $B$ **按行**切成 4 份，每张卡拿一整行：

```
B（4×4矩阵，Layer2）按行切：
GPU0拿B的第1行: [b11,b12,b13,b14]
GPU1拿B的第2行: [b21,b22,b23,b24]
GPU2拿B的第3行: [b31,b32,b33,b34]
GPU3拿B的第4行: [b41,b42,b43,b44]

最终要算的是 Z = Y @ B（Y是长度4的行向量），
Z 的每个元素 = Y1*B第1行 + Y2*B第2行 + Y3*B第3行 + Y4*B第4行 逐项加总

但每张卡现在只有自己算出的那一个 Y_i，和 B 对应的第 i 行：
  GPU0: 只能算出 Y_1 * [b11,b12,b13,b14] = 部分和1（是Z的"一部分贡献"，不是最终结果）
  GPU1: 只能算出 Y_2 * [b21,b22,b23,b24] = 部分和2
  GPU2: 只能算出 Y_3 * [b31,b32,b33,b34] = 部分和3
  GPU3: 只能算出 Y_4 * [b41,b42,b43,b44] = 部分和4

真正的 Z = 部分和1 + 部分和2 + 部分和3 + 部分和4（四个长度为4的向量逐元素相加）
         ↓ 这就必须靠 AllReduce 来完成
       AllReduce 后，4张卡都拿到完整、正确的 Z
```

这就是为什么"列切+行切"配对使用：列切让 GELU 前不需要通信，行切让两层矩阵之间只需要在最后**一次性** AllReduce，而不是每一小步都通信。

#### 5.7.3 和 DP 的本质区别，一句话说清楚

```
DP系列：4张卡，4份不同的数据（4个不同句子），各自独立算出4份不同的结果，靠通信"拉齐"成一份
TP：    4张卡，同一份数据（同一个句子），一起合作算同一层的计算，靠通信"拼接/求和"成一份完整结果

DP的通信：发生在"一轮训练结束、要更新参数之前"（次数少，一轮一两次）
TP的通信：发生在"模型内部，每一层甚至每一层内部"（次数多，一层就要通信一次，
          上面例子里仅两层矩阵就要 1 次 AllReduce，200层模型可能就要 100 次以上）
```

这就是为什么 TP 对卡间带宽要求极高，通常只能在一台机器内的多张卡之间用（走 NVLink 高速互联，带宽可达数百 GB/s），跨机器用 TP 会因为通信太慢（跨机带宽通常只有卡内的几分之一到几十分之一）而完全跑不动。

### 5.8 加入 PP：把"层"拆开分给不同卡

如果不是单层矩阵太大，而是层数太多（比如从 2 层变成 200 层，模型总参数很大，但单层矩阵本身能塞进一张卡），这时候更适合按层切。继续沿用 5.1 的例子，但把"2 层"想象成扩展到了 200 层（每层仍然是能塞进一张卡的普通大小）：

```
PP 的做法：把 200 层模型按顺序切成 4 段，一张卡负责一段连续的层
  GPU0: 负责 Layer 1~50
  GPU1: 负责 Layer 51~100
  GPU2: 负责 Layer 101~150
  GPU3: 负责 Layer 151~200
```

#### 5.8.1 具体走一遍数据流：一个 batch 是怎么"接力"过去的

假设输入是一个 batch 的数据 $X_0$（比如 8 条句子）：

```
时刻1：GPU0 计算 Layer1~50，输入是 X_0，算出中间结果 X_1（形状不变，比如还是 [8, seq_len, hidden]）
       GPU1、GPU2、GPU3 此时都还没有任何数据，处于空闲等待

时刻2：GPU0 通过 Send 把 X_1 发给 GPU1（点对点通信，只发给这一个人，不广播给GPU2/GPU3）
       GPU1 通过 Recv 接收到 X_1，开始计算 Layer51~100，算出 X_2
       GPU0 这时候已经没有当前这个batch的活干了（但显存里还留着算梯度要用的中间激活值）
       GPU2、GPU3 依然空闲

时刻3：GPU1 把 X_2 Send 给 GPU2，GPU2 计算 Layer101~150，得到 X_3
       GPU0、GPU1 空闲

时刻4：GPU2 把 X_3 Send 给 GPU3，GPU3 计算 Layer151~200，得到最终输出 Y，算 loss
       GPU0、GPU1、GPU2 全部空闲

反向传播时反过来：GPU3 算出的梯度 Send 回 GPU2 → GPU1 → GPU0，依次反向传播
```

这里的通信和 TP、DP 都不一样：不是 AllReduce（求和拉齐所有卡），也不是 AllGather（拼出完整参数），而是**点对点的 Send/Recv**——GPU0 只需要把它算完的那"一段中间结果 $X_1$"发给下一个人 GPU1，不需要像 AllReduce 那样让所有卡都参与、都拿到同一份数据。通信量也很小：只需要传输"层与层之间的激活值"（通常远小于该层的权重矩阵大小），而不是传输梯度或参数。

#### 5.8.2 核心问题：Bubble（气泡）

把上面 4 个时刻画成时间线就能看出问题：

```
        时刻1      时刻2      时刻3      时刻4
GPU0:  [算Layer1-50]  空闲        空闲        空闲
GPU1:     空闲     [算Layer51-100] 空闲        空闲
GPU2:     空闲        空闲     [算Layer101-150] 空闲
GPU3:     空闲        空闲        空闲     [算Layer151-200]

任意时刻，4张卡里只有1张在真正干活，其余3张都在"空转"（这就是Bubble/气泡）
4张卡，理论上应该4倍加速，实际上因为这种串行等待，加速比远小于4
```

这就是为什么朴素 PP（一次性把整个 batch 从头传到尾）几乎不会真正拿来用——GPU 利用率太低了。解决办法是把一个大 batch 切成很多个 **micro-batch**，让 GPU0 算完第 1 个 micro-batch 立刻开始算第 2 个，不用等 GPU1/2/3 把第 1 个 micro-batch 处理完，从而把"空闲的格子"逐渐填满（GPipe 方式、Megatron 的 1F1B 方案），完整的原理和图解见 [六、流水线并行的 Bubble 问题详解](#六流水线并行的-bubble-问题详解)。

### 5.9 加入 SP：TP 的"补丁"，把序列维度也切开

前面 5.7 节的 TP 例子里，AllReduce 之后每张卡都拿到了完整的 $Z$（形状是 `[batch, seq_len, hidden]`）。但如果模型里紧接着有一个 **LayerNorm**（几乎每个 Transformer Block 都有），会出现一个容易被忽略的浪费：

```
TP 区域内（列切+行切的 Linear 层）：显存里存的是"按 hidden 维度切开"的张量分片，
  每张卡只存 1/4 的 hidden 维度 → 省显存

但 LayerNorm、Dropout 这类操作不是"按矩阵切分"的方式并行的：
  LayerNorm 需要对完整的 hidden 维度求均值/方差，
  Dropout 只是逐元素独立地随机丢弃，
  这两者都不涉及"大矩阵乘法"，所以传统 TP 不会去切它们，
  而是在 AllReduce 之后，让每张卡都拿着"完整"的激活值去跑 LayerNorm/Dropout

问题：4张卡，每张卡都存了一份完整的激活值（同样的数据重复了4份），显存被浪费
```

SP（序列并行）的做法：既然 LayerNorm/Dropout 是**逐 token 独立**的操作（每个 token 的计算不依赖其他 token），完全可以按**序列长度**（seq_len 维度）而不是 hidden 维度切开：

```
假设一个 batch 的序列长度 seq_len = 8（8个token），4张卡：
TP区域（Linear层）：按 hidden 维度切，每张卡负责 1/4 的 hidden，但 8 个 token 全部都在
SP区域（LayerNorm/Dropout）：按 seq_len 维度切，每张卡只负责 2 个 token 的 LayerNorm

  GPU0: 负责 token 1~2 的 LayerNorm（hidden维度是完整的）
  GPU1: 负责 token 3~4 的 LayerNorm
  GPU2: 负责 token 5~6 的 LayerNorm
  GPU3: 负责 token 7~8 的 LayerNorm

每张卡只需要存"自己负责的2个token"的完整hidden向量，而不是"8个token"的完整hidden向量
→ 显存降到 1/4，因为这部分数据不再是4张卡重复存4份
```

代价是：从 TP 区域（按 hidden 切）切换到 SP 区域（按 seq_len 切），中间需要一次 **AllGather**（把 hidden 维度拼完整，同时按 seq_len 重新分配）；从 SP 区域再切回 TP 区域时，需要一次 **Reduce-Scatter**（配合行切的 AllReduce 一起做，等价于拆开的实现）。

```
一句话总结 SP：
  TP 只切了"矩阵计算"部分的显存（Linear层的权重和中间结果），
  但 LayerNorm/Dropout 这些"矩阵计算之外"的激活值，TP 管不到，还是重复存了 N 份，
  SP 就是专门补上这个洞——用 seq_len 维度把这部分也切开，配合 TP 使用（合称 TP+SP），
  不引入新的独立并行方式，只是"顺便"把 TP 漏掉的那部分显存也省下来
```

### 5.10 四种并行放在一起，各自"切的维度"完全不同

```
┌────────────────────────────────────────────────────────┐
│  DP/DDP/ZeRO/FSDP  →  切【数据】（batch维度）             │
│    每张卡处理不同的句子，模型逻辑上保持完整                 │
│    通信：AllReduce / Reduce-Scatter / AllGather          │
├────────────────────────────────────────────────────────┤
│  TP（张量并行）  →  切【单层内部的矩阵】（hidden维度）      │
│    每张卡处理同一个句子的同一层，但只算这一层的一部分        │
│    通信：AllReduce（每层内部就要通信，次数最多，最费带宽）  │
├────────────────────────────────────────────────────────┤
│  PP（流水线并行） →  切【层与层之间】（depth/层数维度）      │
│    每张卡负责完整的若干层，像接力赛一样传递中间结果          │
│    通信：Send/Recv（点对点，只发给下一棒，不广播）          │
├────────────────────────────────────────────────────────┤
│  SP（序列并行，TP的搭档） →  切【序列长度】（seq_len维度）  │
│    在TP区域内，把LayerNorm/Dropout这类逐token独立的操作     │
│    按 token 位置切开，进一步省显存                          │
└────────────────────────────────────────────────────────┘
```

四者可以同时叠加使用（这就是"3D 并行"，加上 ZeRO 就是"3D+ZeRO"），假设现在模型变成了"8 层、每层矩阵都很大"，16 张卡可以这样分配：

```
16张卡分成 2组 PP阶段 × 2组 TP切分 × 4组 DP副本：

PP维度（2）：GPU组A负责Layer1~4，GPU组B负责Layer5~8
TP维度（2）：每个PP组内部，矩阵再切成2份放在2张卡上
DP维度（4）：上面这一整套（PP+TP组合）再复制4份，处理4份不同的数据

16 = 2(PP) × 2(TP) × 4(DP)
```

决定用哪种并行、切多少份，取决于"卡不够用的原因是什么"：

```
单层矩阵太大，一张卡塞不下这一层 → 上 TP
层数太多，模型总层数塞不进一张卡的显存 → 上 PP
显存主要被"参数+梯度+优化器状态的冗余副本"占满 → 上 ZeRO/FSDP
纯粹卡数量够、只是想让训练更快（数据量大）→ 上 DP/DDP 就行，不需要TP/PP
```

### 5.11 DP/DDP/ZeRO/FSDP 本质上都是同一种并行范式

一个容易搞混但很重要的归纳：**DP、DDP、ZeRO-1/2/3、FSDP 这五个东西本质上都是数据并行（Data Parallelism）**，判断标准很简单，只看一件事：

```
判断是不是"数据并行"的唯一标准：
  每张卡处理的【输入数据】是不是不同的？

DP:        ✅ 是，每卡不同的 batch
DDP:       ✅ 是，每卡不同的 batch
ZeRO-1/2/3:✅ 是，每卡不同的 batch
FSDP:      ✅ 是，每卡不同的 batch

只要这一点成立，就属于数据并行家族，不管内部怎么存参数/梯度/优化器状态
```

对比一下 TP、PP，就更清楚这个判断标准为什么成立：

```
TP:  ❌ 不是，所有卡处理的是【同一个 batch 的同一份数据】，只是算的是这份数据里"同一层的不同部分"
PP:  ❌ 不是，所有卡处理的也是【同一个 batch 的同一份数据】，只是算的是"不同的层"
```

那 DP → DDP → ZeRO-1 → ZeRO-2 → ZeRO-3/FSDP 这条线，到底在演进什么？**演进的是"每张卡内部怎么存参数/梯度/优化器状态"这件事，而不是"数据要不要切"这件事**——数据切分（并行范式本身）从头到尾都没变过：

```
DP    ：数据切分 + 每卡存【完整】的参数/梯度/优化器状态（最原始，冗余最大）
DDP   ：数据切分 + 每卡存【完整】的一切，只是通信时机更聪明（overlap），本质存储方式和DP一样
ZeRO-1：数据切分 + 优化器状态【切分】，参数/梯度还是完整的
ZeRO-2：数据切分 + 优化器状态+梯度【都切分】，参数还是完整的
ZeRO-3：数据切分 + 参数/梯度/优化器状态【全部切分】，用时才临时拼出来
FSDP  ：数据切分 + 存储方式等价于 ZeRO-3（PyTorch 官方叫法不一样，内核思想一样）
```

一句话说清楚这条演进主线：

```
不变的：并行范式 = 数据并行（每卡处理不同数据）
在变的：显存存储策略 = 从"完全不切、大量冗余"逐步进化到"切得越来越碎、冗余越来越少"
```

**一个容易被"FSDP"这个名字误导的点**："Fully Sharded Data Parallel"——注意这个名字里明确写着 Data Parallel，PyTorch 官方自己都在名字里承认了它的本质是数据并行，只是"Fully Sharded"（完全分片存储）修饰的是"存储方式"，不是"并行范式"。很多人第一次看到 FSDP 会以为它是和 TP、PP 平级的、全新的一种并行方式，但其实它和 DP/DDP 是同一个范式下的不同存储策略，和 ZeRO-3 是同一个思想的两种不同实现（一个来自 DeepSpeed，一个来自 PyTorch 官方）。

结论：DP、DDP、ZeRO-1/2/3、FSDP 这一整条线，从"并行范式"这个维度看，全部都是数据并行；真正跳出数据并行、开辟新维度的，只有 TP（切模型内部矩阵）、PP（切模型层数）、SP（切序列长度）这三个。

### 5.12 把 DeepSpeed、Megatron、Accelerate、TRL 串进这条故事线

上面 DP/DDP/ZeRO/TP/PP/SP 都还只是"思想/方法论"——知道该怎么切。但真正把这些思想写成能跑的代码、处理好底层的通信细节（比如什么时候该 AllReduce、什么时候该 AllGather、怎么 overlap 计算和通信），是很复杂的工程活，这就是"框架"要做的事：

```
DeepSpeed（微软）  的强项：ZeRO（1/2/3）的完整工程实现，还带 ZeRO-Offload
   → 对应例子里的：怎么把"优化器状态/梯度/参数"自动切分、自动通信
   → 你只需要写个 json 配置文件，不用改模型代码

Megatron-LM（英伟达）的强项：TP + PP 的完整工程实现（3D并行）
   → 对应例子里的：怎么把"一层矩阵"或"多层"自动切给多卡、自动插入AllReduce/Send-Recv
   → 代价：需要把模型里的 nn.Linear 换成它提供的 ColumnParallelLinear/RowParallelLinear
```

**为什么经常看到"Megatron-DeepSpeed"这种组合用法？** 因为两者负责的是完全不同的切分维度，天然互补，不冲突：

```
Megatron 负责：TP（切层内矩阵）+ PP（切层与层）
DeepSpeed 负责：在 Megatron 切完之后剩下的"DP维度"上，再用 ZeRO 进一步压缩显存

回到 16卡的例子：
  Megatron 先把16卡分成 2(PP) × 2(TP) = 4张卡一组，一共4组
  每组内部4张卡，处理的是"同一份数据的不同层/不同矩阵切片"（TP+PP，不是DP）
  4组之间，处理的是"不同的数据"（这才是DP维度）
  → DeepSpeed 的 ZeRO 就作用在这"4组之间"这个DP维度上，把每组内的优化器状态等再切一次
```

**Accelerate 是什么角色？**——它不是新的并行思想，而是"帮你自动选择用 DDP 还是 FSDP 还是 DeepSpeed"的统一接口：

```
你写同一份训练代码：
  model, optimizer, dataloader = accelerator.prepare(model, optimizer, dataloader)

Accelerate 根据你的配置文件，自动决定底层实际用：
  配置1 → 底层用普通 DDP
  配置2 → 底层用 PyTorch FSDP（对应 ZeRO-3）
  配置3 → 底层用 DeepSpeed（ZeRO-1/2/3 任选）

好处：你不需要为每种底层引擎单独改一遍训练代码
```

**TRL 又是什么角色？**——它站在 Accelerate 之上，专门封装"怎么做 SFT/DPO/GRPO 训练"这个业务逻辑，比如 loss 怎么算、要不要跑一个 reference model、奖励怎么归一化，这些和"分布式"完全无关的算法层面的事，底层的通信、显存切分全部甩给 Accelerate 再往下传给 DDP/FSDP/DeepSpeed。

完整的层次关系，串成一张图（呼应第一章的层次图，这里补上 TP/PP/SP 和 Megatron 的位置）：

```
┌───────────────────────────────────────────────────────┐
│ 你的代码：只关心"怎么写SFT/DPO/GRPO的训练逻辑"           │
├───────────────────────────────────────────────────────┤
│ TRL / verl / OpenRLHF：封装好训练循环、loss计算           │
├───────────────────────────────────────────────────────┤
│ Accelerate：统一接口，自动适配底层用哪个引擎               │
├───────────────────────────────────────────────────────┤
│ DeepSpeed          │  Megatron-LM        │ PyTorch FSDP │
│ 实现 ZeRO 1/2/3     │  实现 TP + PP(3D并行)│ 实现 ZeRO-3   │
├───────────────────────────────────────────────────────┤
│         底层思想：DP / DDP / ZeRO / TP / PP / SP         │
├───────────────────────────────────────────────────────┤
│                  PyTorch + NCCL + CUDA                  │
└───────────────────────────────────────────────────────┘

对应关系：
DeepSpeed  ←→ 主要实现"切数据这条线"里的显存优化(ZeRO)
Megatron   ←→ 主要实现"切模型这条线"里的TP和PP
两者结合(Megatron-DeepSpeed) ←→ 4种并行全部叠加使用(3D并行+ZeRO)
Accelerate ←→ 不实现任何新算法，只是帮你"选用哪个底层引擎"的统一开关
TRL        ←→ 不管底层是谁，只管"SFT/DPO/GRPO这些对齐算法怎么写loss"
```

### 5.13 这些技术哪些训练用、哪些推理用

先明确训练和推理的本质区别，这是判断"谁用在哪"的关键：

```
训练时显存里有：参数 + 梯度 + 优化器状态 + 激活值   ← 四样东西都要存
推理时显存里有：参数 + KV Cache + 少量激活值        ← 没有梯度、没有优化器状态！

训练要做 backward（反向传播），推理只做 forward（只需要一路往前算）
```

这个区别直接决定了：ZeRO/FSDP 这套"优化器状态怎么切"的技术，在推理阶段根本没有意义——推理没有优化器状态，也没有梯度，可切的东西完全不是同一批。

逐个过一遍，标清楚"训练专属 / 推理专属 / 两边都能用"：

```
┌─────────────────────────────────────────────────────────┐
│ 训练专属（推理时用不上，因为解决的是梯度/优化器状态的问题） │
├─────────────────────────────────────────────────────────┤
│ DP / DDP        ← 只有"算梯度、更新参数"这个过程需要多卡同步数据
│ ZeRO-1/2/3      ← 切的是优化器状态和梯度，推理根本没有这两样东西
│ FSDP            ← 同上，本质是ZeRO-3，训练专属
│ DeepSpeed       ← 核心卖点就是ZeRO，训练框架
│ 混合精度+LossScaling ← 是为了梯度计算/更新不下溢，推理不做反向传播，用不上
├─────────────────────────────────────────────────────────┤
│ 推理专属（训练时不存在这个问题）                          │
├─────────────────────────────────────────────────────────┤
│ KV Cache        ← 只有自回归生成时才需要缓存历史Key/Value
│ PagedAttention  ← 专门管理KV Cache的显存碎片问题
│ Continuous Batching / Chunked Prefill ← 推理服务调度技术
│ 采样策略(Top-p/Top-k/Temperature) ← 只在生成阶段用
├─────────────────────────────────────────────────────────┤
│ 训练和推理都能用（只是"切的对象"变了）                    │
├─────────────────────────────────────────────────────────┤
│ TP（张量并行）  ← 训练时切矩阵做forward+backward；推理时只做forward，同样可以切矩阵分摊到多卡
│ PP（流水线并行）← 训练/推理都可以按层切分到不同卡
│ SP（序列并行）  ← 训练/推理都能按序列维度切
│ Megatron-LM     ← 本身主要是训练框架，但它的TP实现思路，推理框架（如vLLM的张量并行）也是借鉴同样的思想
│ eager/SDPA/FlashAttention ← Attention计算这个数学操作，训练的forward和推理的forward用的是同一套优化，训练时backward也会受益于FlashAttention（反向传播同样能省显存）
└─────────────────────────────────────────────────────────┘
```

用一张图对齐"训练管线" vs "推理管线"分别用了什么：

```
训练管线：
数据 → 切分给多卡(DP/DDP) → 模型太大再切(TP/PP) → forward+backward
                                                        ↓
                                      梯度/优化器状态太占显存 → 上 ZeRO/FSDP
                                                        ↓
                                      算得慢 → FlashAttention/混合精度加速
                                                        ↓
                                      框架封装：DeepSpeed(ZeRO) / Megatron(TP+PP) / Accelerate(统一接口) / TRL(算法层)


推理管线：
用户请求 → 模型太大一张卡装不下 → 上 TP/PP（跟训练思路一样，只是没有backward）
                                        ↓
                            自回归生成，需要存历史KV → KV Cache
                                        ↓
                            多用户请求，KV Cache显存碎片化 → PagedAttention
                                        ↓
                            Attention计算本身要快 → FlashAttention/SDPA
                                        ↓
                            多个请求怎么高效凑批处理 → Continuous Batching/Chunked Prefill
                                        ↓
                            框架封装：vLLM / TensorRT-LLM / SGLang
```

**特别说明：TRL/verl/OpenRLHF 这些"训练框架"，为什么也会用 vLLM（推理框架）？**

因为 RLHF/GRPO 训练本身包含"生成（rollout）"这一步——模型需要先像推理一样生成一批回答，再对这些回答算 reward、算 loss、做梯度更新。所以 RLHF 训练是训练和推理交替进行的：

```
GRPO一轮迭代：
  用 vLLM（推理引擎）快速生成一批回答  ← 这一步是"推理"，用KV Cache/PagedAttention这套
       ↓
  用 DeepSpeed/FSDP（训练引擎）对这批回答算loss、做backward、更新参数 ← 这一步是"训练"，用ZeRO这套
```

这也是为什么 [verl.md](verl.md) 笔记里提到"训练用 Megatron/FSDP，推理（rollout）用 vLLM，两者解耦"——本质上就是把"训练专属技术栈"和"推理专属技术栈"在同一个训练流程里分工使用。

**一句话总结记忆**：判断一个技术是训练专属还是推理专属，只要问自己"它解决的问题里有没有涉及梯度或优化器状态"——有，就是训练专属（DP/DDP/ZeRO/FSDP）；跟"自回归生成、多轮解码"有关，就是推理专属（KV Cache/PagedAttention/采样策略）；如果只是"矩阵/层怎么切到多卡上算得动、算得快"这种和 forward 本身相关的技术（TP/PP/SP/FlashAttention），训练推理两边都用得上，只是训练时多了一步 backward 要考虑。

### 5.14 实操细节：用 DP/FSDP 时 batch size 要不要凑 GPU 的倍数

先分清楚"batch size"这个词在多卡场景下容易混淆的两层含义：

```
per_device_batch_size（每张卡的 batch）  ← 你在代码里 DataLoader 设置的那个数字
global_batch_size（全局有效 batch）      ← 全部N张卡一起处理的总样本数

global_batch_size = per_device_batch_size × N（GPU数量）× 梯度累积步数
```

**直接回答**：不是"取 GPU 的倍数才有意义"，而是"总样本数不能被 GPU 数整除时会有点小麻烦，但不是不能用"。准确的说法是：你设置的 `per_device_batch_size` 本身不需要是 GPU 数的倍数（这个数字是你自己指定的，比如每卡 8 条，不存在"是不是 GPU 倍数"的问题）。真正容易出问题的地方是——**数据集的总样本数，能不能被 `per_device_batch_size × GPU数` 整除**。

具体会发生什么问题：

```
假设：4张卡（N=4），per_device_batch_size=8，所以每一"轮"总共处理 32 条数据

如果数据集总共有 1000 条：
  1000 ÷ 32 = 31 轮，余 8 条
  最后剩下的这8条，没办法平均分给4张卡（每卡该分2条，够分），这种情况其实还好，能分匀

如果数据集总共有 1001 条：
  1001 ÷ 32 = 31 轮，余 9 条
  最后剩这9条，分给4张卡：GPU0拿3条，GPU1拿3条，GPU2拿2条，GPU3拿1条
  ← 每张卡拿到的数据量不一样多！
```

为什么"每张卡数据量不一样"是个问题？

```
DDP/FSDP 靠 AllReduce/Reduce-Scatter 同步梯度，这个操作要求：
  参与通信的每张卡，必须都调用一次这个通信操作，次数要对齐

如果 GPU3 只分到1条数据、提前算完一个batch结束了，
而 GPU0 还有3条数据、还要再算一个mini-batch，
GPU3 这时候会在通信点上"空等"，甚至直接报错（因为它已经没有下一批数据可以配合通信了）
```

实际框架是怎么处理这个问题的？PyTorch 的 `DistributedSampler` 默认提供两种处理方式：

```python
# 方式一：drop_last=True（丢弃多余的，最常用）
sampler = DistributedSampler(dataset, num_replicas=4, rank=rank, drop_last=True)
# 1001条数据，丢掉最后9条凑不齐的，实际只用992条（31×32）
# 好处：每张卡数据量严格一致，简单省心
# 代价：极少数样本没用上，通常无关紧要

# 方式二：drop_last=False（默认），会自动"重复填充"凑齐
# 1001条数据，会重复采样前几条数据，凑够 1004条（32的倍数），保证能分匀
# 好处：数据一条不丢
# 代价：极少数样本在这一个epoch里被重复训练了一次
```

所以结论是：你完全不需要手动去让 batch size 凑成 GPU 数的倍数，框架的 `DistributedSampler` 已经自动帮你处理"数据集总量除不尽"这个边界情况了（丢弃或重复垫底，两种策略都不影响训练效果）。

**什么时候"是不是 GPU 的倍数"真正会影响效果，而不只是边界处理？** 有一种情况需要自己留意，不是框架能自动兜底的：

```
如果你的 per_device_batch_size 设置得很小、GPU数量很多，
导致 global_batch_size 变化时，你没有相应调整学习率，
这会影响收敛效果 —— 但这是"学习率要不要跟着 batch size 缩放"的问题（linear scaling rule），
跟"是否整除"完全是两回事，不要混淆
```

以及 FSDP/TP 场景下真正需要注意"整除"的地方，**不是 batch，而是模型维度**：

```
TP 切分矩阵时：hidden_size 必须能被"张量并行的卡数"整除
  比如 hidden_size=4096，用8卡做TP，4096÷8=512，正好切匀 ✅
  如果 hidden_size=4097，8卡就切不匀了，会报错或者需要padding

GQA/MQA 场景：num_attention_heads 必须能被 num_key_value_heads 整除
  这个和分布式并行无关，是模型结构本身的要求（repeat_kv 的前提）
```

**一句话总结**：batch size 不需要你手动凑成 GPU 数的倍数——`DistributedSampler` 会自动用"丢尾数"或"重复填充"兜底，你不用管；真正需要你手动保证"能整除"的地方，是 TP 场景下的 `hidden_size`、`num_heads` 这些模型结构维度要能被"并行的卡数"整除，这个如果没对齐，程序会直接报错，不是训练效果打折扣的问题，而是根本跑不起来。

#### 5.14.1 案例：verl 里 mini_batch/micro_batch 参数在多卡下怎么分配

以 verl/GRPO 训练为例（参数含义详见 [verl.md · 6.13 Batch 相关参数详解](verl.md#613-batch-相关参数详解-train_batch_size--rolloutn--mini_batch--micro_batch)），假设双卡 FSDP，配置为：

```
ROLLOUT_N=4，TRAIN_BATCH_SIZE=4，MINI_BATCH_SIZE=4，MICRO_BATCH_SIZE=1（这个是 per_gpu 粒度）
```

注意参数名字通常带 `_per_gpu` 后缀（如 `ppo_micro_batch_size_per_gpu`），说明这个数字本来就是"每张卡"的粒度，不是全局的。逐层展开：

```
第一层（和卡数无关，先产生数据）：
  train_batch_size(4个prompt) × rollout.n(4条/prompt) = 16 条 rollout 样本

第二层（也是全局的，和卡数无关）：mini_batch 切分
  16条 ÷ mini_batch_size=4 = 4 次梯度更新

第三层：★ 这里开始，卡数就要参与计算了
  每个 mini_batch 是 4 条数据，这 4 条数据要分给【双卡】
  双卡场景下，DDP/FSDP 会把这 4 条数据平均分给 2 张卡：
    GPU0 分到 2 条
    GPU1 分到 2 条

  然后每张卡上，还要按 micro_batch_size_per_gpu=1 继续切
    GPU0：2条 ÷ 1 = 做 2 次 micro-batch（梯度累积2次）
    GPU1：2条 ÷ 1 = 做 2 次 micro-batch（梯度累积2次）

  GPU0和GPU1【同时并行】各自做自己的2次累积，不是排队等
```

容易想岔的地方："`MICRO_BATCH_SIZE=1` 是不是每次前向只处理 1 条数据，训练效果不就打折扣了？"——`MICRO_BATCH_SIZE=1` 指的是"每次 forward+backward 只喂 1 条数据"，但这不代表"整个 mini_batch 就只处理 1 条数据"——1 条数据只是被切碎、分批喂进去，累积够了才更新一次：

```
单卡时：mini_batch=4条，micro_batch=1
  → 1条 forward+backward → 1条 forward+backward → 1条 → 1条
  → 4次都做完，累积够4条的梯度 → 才 optimizer.step()
  → 这4次是【串行】的，一张卡一次只能算1条

双卡时：mini_batch=4条 分给2张卡，每卡2条，每卡micro_batch=1
  → GPU0：1条 forward+backward → 1条 forward+backward（串行2次，累积2条的梯度）
  → GPU1：1条 forward+backward → 1条 forward+backward（串行2次，累积2条的梯度）
  → GPU0和GPU1【同时在跑】，跑完后 AllReduce 汇总两卡的梯度 → 一起 optimizer.step()

  最终效果：还是凑齐了4条数据的梯度才更新，和单卡逻辑上完全一致，
  只是双卡把"4次串行的micro-batch"变成了"2张卡各2次串行，但两卡是并行执行的"
  → 速度理论上快了接近2倍，符合预期的加速效果，不是"有问题"
```

唯一需要留意的仍然是"能否整除"（呼应上一节）：

```
mini_batch_size=4，要分给2张卡 → 4÷2=2，正好整除 ✅ 没问题
如果 mini_batch_size=3，分给2张卡 → 3÷2 除不尽 ⚠️ 这时才是真正需要担心的场景
   （框架通常会要求 mini_batch_size 必须能被 GPU 数整除，否则报错或行为不确定）
```

## 六、流水线并行的 Bubble 问题详解

### 6.1 Bubble 是怎么产生的

流水线并行把模型按层切给多张卡，数据必须按顺序依次流过：GPU0 算完 → 传给 GPU1 → GPU1 算完 → 传给 GPU2 ...

```
前向传播阶段（朴素流水线，只有 1 个大 batch）：

时间轴 →→→→→→→→→→→→→→→→→→→→→→→→

GPU0: [算batch] [空闲] [空闲] [空闲]
GPU1: [空闲]    [算batch] [空闲] [空闲]
GPU2: [空闲]    [空闲]  [算batch] [空闲]
GPU3: [空闲]    [空闲]  [空闲]  [算batch]

GPU0 算完就闲置了，要等 GPU1/2/3 依次算完
→ 大量 GPU 时间浪费在等待（Bubble）上
```

加上反向传播后 Bubble 问题更严重：

```
Bubble 比例 = (GPU数 - 1) / GPU数

4 张卡 → Bubble 占比 = 3/4 = 75%！
→ 相当于 4 张卡里有 3 张在大部分时间空转
```

### 6.2 Micro-batch 如何缓解 Bubble（GPipe 方式）

**核心思想**：与其等一个大 batch 全部算完，不如把它切成很多个小的 micro-batch，让流水线上的每个阶段持续有活干，类似工厂流水线不等一辆车完全组装好才开始下一辆。

```
把 1 个 batch 切成 4 个 micro-batch（m1, m2, m3, m4）：

时间轴 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→

GPU0: [F,m1][F,m2][F,m3][F,m4]    [B,m4][B,m3][B,m2][B,m1]
GPU1:      [F,m1][F,m2][F,m3][F,m4][B,m4][B,m3][B,m2][B,m1]
GPU2:           [F,m1][F,m2][F,m3][F,m4][B,m4][B,m3][B,m2][B,m1]
GPU3:                [F,m1][F,m2][F,m3][F,m4][B,m4][B,m3][B,m2][B,m1]

Bubble 只在流水线的开头和结尾（图中留白部分），中间阶段各卡持续工作
```

**Bubble 比例公式**：

$$\text{Bubble 比例} = \frac{p-1}{m+p-1}$$

其中 $p$ 是流水线阶段数（GPU 数），$m$ 是 micro-batch 数量。

| $p$（GPU数） | $m$（micro-batch数） | Bubble 比例 | 说明 |
|---|---|---|---|
| 4 | 1（无 micro-batch） | $3/4 = 75\%$ | 很差 |
| 4 | 4 | $3/7 \approx 43\%$ | 好一些 |
| 4 | 8 | $3/11 \approx 27\%$ | 更好 |
| 4 | $\to \infty$ | $\to 0\%$ | 理想情况 |

结论：micro-batch 数量越多，Bubble 越少；但这引出了下一个问题——显存开销。

### 6.3 GPipe 的新问题：显存随 micro-batch 数线性增长

GPipe 虽然用 micro-batch 减少了 Bubble，但每张卡要把 **所有 micro-batch 的前向激活值都保存在显存里**，等反向传播时才用得上：

```
GPU0: [F,m1][F,m2][F,m3][F,m4]...

GPU0 要把 m1,m2,m3,m4 的激活值全部保存在显存里，等反向传播时用！
→ 显存占用 = micro-batch 数量 × 单个激活值大小
→ micro-batch 越多，显存压力越大
→ 和"减少 Bubble 需要更多 micro-batch"这个目标直接矛盾！
```

### 6.4 Megatron 的解决方案：1F1B（One Forward One Backward）

**核心思路**：不等所有 micro-batch 的前向全部算完再统一做反向，而是**算完一个 micro-batch 的前向就立刻做它对应的反向**，从而及时释放这个 micro-batch 占用的激活值显存。

```
时间轴 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→

GPU0: [F1][F2][F3][F4][B4][B3][B2][B1]
GPU1:    [F1][F2][F3][F4][B4][B3][B2][B1]
GPU2:       [F1][F2][F3][F4][B4][B3][B2][B1]
GPU3:          [F1][F2][F3][F4][B4][B3][B2][B1]

稳定阶段：每个 GPU 交替做前向和反向
  → 显存占用恒定（只需同时保存 p 个 micro-batch 的激活值，而不是 m 个）
  → Bubble 比例和 GPipe 相同（公式不变）
  → 但显存大幅减少！
```

> 注：不同资料对 1F1B 稳定阶段的具体调度时序描述略有差异（比如各卡进入"1 前向 1 反向"交替模式的起始时机不同），但核心结论一致：显存占用从 $O(m)$（GPipe，随 micro-batch 数增长）降低到 $O(p)$（1F1B，只随流水线阶段数增长），这是 1F1B 相对 GPipe 的核心改进。

### 6.5 Megatron 的进阶方案：Interleaved 1F1B

普通 1F1B 中每张卡负责**连续**的若干层：

```
GPU0: [Layer 1-8]
GPU1: [Layer 9-16]
```

Interleaved（交错）1F1B 让每张卡负责**不连续的多个层段**：

```
GPU0: [Layer 1-4]  + [Layer 17-20]
GPU1: [Layer 5-8]  + [Layer 21-24]
GPU2: [Layer 9-12] + [Layer 25-28]
GPU3: [Layer 13-16]+ [Layer 29-32]
```

效果：Bubble 比例可以进一步降低（大致按每卡负责的段数 $v$ 缩减），代价是通信量相应增加（每卡需要在更多层边界处收发激活值/梯度）。

### 6.6 完整方案对比

| 方案 | Bubble | 显存 | 复杂度 |
|------|--------|------|--------|
| 朴素流水线（无 micro-batch） | 75% | 低 | 简单 |
| GPipe（micro-batch） | 显著降低 | 高（随 $m$ 增长） | 中等 |
| 1F1B | 与 GPipe 相同 | 低（恒定为 $O(p)$） | 中等 |
| Interleaved 1F1B | 更低 | 低 | 复杂（通信量增加） |

**核心矛盾与结论**：Bubble 减少需要更多 micro-batch，而显存节省需要更少 micro-batch；1F1B 通过"算完一个前向立刻做对应反向"打破了这个矛盾，在不增加 Bubble 的前提下把显存占用降了下来，是目前较好的平衡方案。

## 七、通信原语：AllReduce、Scatter、Reduce-Scatter 到底有什么区别

### 7.1 完整的集合通信操作列表

```
Broadcast        一对多（复制同一份数据给所有人）
Scatter          一对多（切片分发，各人拿到不同的一片）
Gather           多对一（收集，Scatter 的反向操作）
Reduce           多对一（带计算，如求和/求平均）
AllGather        多对多（每人收集到所有人的完整数据）
AllReduce        多对多（带计算，结果同步给所有人）
Reduce-Scatter   多对多（先 Reduce 再 Scatter）
AllToAll         多对多（转置式交换，每人给每人发一份不同的数据）
```

### 7.2 逐个图解

**Broadcast（广播）**：一个节点把完整数据发给所有人。

```
GPU0: [A]  ──→  GPU0: [A]
GPU1: [ ]  ──→  GPU1: [A]
GPU2: [ ]  ──→  GPU2: [A]
```
场景：把模型参数从主节点广播给所有卡（初始化时同步权重）。

**Scatter（散播）**：一个节点把数据**切片**分发给所有人，每人拿到不同的一片。

```
GPU0: [A,B,C,D]  ──→  GPU0: [A]
                       GPU1: [B]
                       GPU2: [C]
                       GPU3: [D]
```
场景：把数据集切片分发给各卡。

**Gather（收集）**：Scatter 的反向操作，所有节点的数据汇集到一个节点。

```
GPU0: [A]  ┐
GPU1: [B]  ├──→  GPU0: [A,B,C,D]
GPU2: [C]  ┤
GPU3: [D]  ┘
```

**Reduce（规约）**：所有节点数据汇集到一个节点，并做计算（求和/求平均）。

```
GPU0: [1]  ┐
GPU1: [2]  ├──→  GPU0: [1+2+3+4=10]
GPU2: [3]  ┤
GPU3: [4]  ┘
```
场景：把所有卡的 loss 汇总到主卡打印。

**AllGather（全收集）**：每个节点都收集所有人的数据，最终每个节点都拥有完整数据（Gather 的"All"版本）。

```
GPU0: [A]  ──→  GPU0: [A,B,C,D]
GPU1: [B]  ──→  GPU1: [A,B,C,D]
GPU2: [C]  ──→  GPU2: [A,B,C,D]
GPU3: [D]  ──→  GPU3: [A,B,C,D]
```
场景：FSDP/ZeRO-3 前向计算时，每张卡只存 1/N 参数，计算前 AllGather 拼出完整参数。

**AllReduce（全规约）**：所有节点数据做计算，结果同步给所有人（本质上 = Reduce + Broadcast 两步合一）。

```
GPU0: [1]  ──→  GPU0: [10]
GPU1: [2]  ──→  GPU1: [10]
GPU2: [3]  ──→  GPU2: [10]
GPU3: [4]  ──→  GPU3: [10]
```
场景：DDP 梯度同步，每张卡算完梯度后 AllReduce 让所有卡的梯度保持一致。

**Reduce-Scatter（规约散播）**：先对所有数据做 Reduce（求和），再把求和结果按分片 Scatter 给各节点，每个节点只得到结果的一部分。

```
输入：
  GPU0: [a0, a1, a2, a3]
  GPU1: [b0, b1, b2, b3]
  GPU2: [c0, c1, c2, c3]
  GPU3: [d0, d1, d2, d3]

输出（每人只得到一段的求和结果）：
  GPU0: [a0+b0+c0+d0]   ← 第0段的总和
  GPU1: [a1+b1+c1+d1]   ← 第1段的总和
  GPU2: [a2+b2+c2+d2]   ← 第2段的总和
  GPU3: [a3+b3+c3+d3]   ← 第3段的总和
```
场景：ZeRO-2/3、FSDP 梯度同步，每张卡只负责保存和更新一部分梯度。

### 7.3 最重要的关系：AllReduce = Reduce-Scatter + AllGather

这是理解现代分布式训练通信优化的关键：

```
第一步 Reduce-Scatter：
  GPU0: [g0,g1,g2,g3]       GPU0: [G0]  ← 只有第0段的汇总
  GPU1: [g0,g1,g2,g3]  ──→  GPU1: [G1]  ← 只有第1段的汇总
  GPU2: [g0,g1,g2,g3]       GPU2: [G2]
  GPU3: [g0,g1,g2,g3]       GPU3: [G3]

第二步 AllGather：
  GPU0: [G0]       GPU0: [G0,G1,G2,G3]  ← 完整梯度
  GPU1: [G1]  ──→  GPU1: [G0,G1,G2,G3]
  GPU2: [G2]       GPU2: [G0,G1,G2,G3]
  GPU3: [G3]       GPU3: [G0,G1,G2,G3]

结果和直接 AllReduce 完全一样，但拆成两步后：
  ZeRO-2/3 可以在 Reduce-Scatter 之后就停止，不再做 AllGather
  → 每张卡只保留自己负责的梯度分片，省下了后一半的显存和通信
```

### 7.4 在训练框架中的实际应用

```
┌──────────────────────────────────────────────────┐
│  DDP 梯度同步：                                   │
│  各卡梯度 → AllReduce → 所有卡梯度一致            │
├──────────────────────────────────────────────────┤
│  FSDP / ZeRO-3 前向传播：                        │
│  各卡只有 1/N 参数 → AllGather → 完整参数         │
│  计算完立刻释放（节省显存）                        │
├──────────────────────────────────────────────────┤
│  FSDP / ZeRO-2/3 反向传播：                      │
│  各卡完整梯度 → Reduce-Scatter → 各卡 1/N 梯度    │
│  每张卡只更新自己负责的那部分参数                  │
├──────────────────────────────────────────────────┤
│  Tensor Parallel：                               │
│  各卡算一半结果 → AllReduce → 合并完整结果        │
└──────────────────────────────────────────────────┘
```

### 7.5 一张表总结 + 记忆口诀

| 操作 | 输入 | 输出 | 典型场景 |
|------|------|------|---------|
| Broadcast | 1 个节点有数据 | 所有人都拿到相同的完整数据 | 参数初始化广播 |
| Scatter | 1 个节点有完整数据 | 各人拿到不同的 1 片 | 数据集切片分发 |
| Gather | 各人各有 1 片 | 1 个节点拿到完整拼接结果 | 结果汇总 |
| Reduce | 各人各有数据 | 1 个节点拿到求和结果 | loss 汇总 |
| AllGather | 各人各有 1 片 | 所有人都拿到完整拼接结果 | FSDP 前向拼参数 |
| AllReduce | 各人各有数据 | 所有人都拿到求和结果 | DDP 梯度同步 |
| Reduce-Scatter | 各人各有数据 | 各人拿到自己那 1 段的求和结果 | FSDP/ZeRO 梯度同步 |

```
记忆口诀：

Scatter   → 一个人把东西分给大家（切片发出去）
Gather    → 大家把东西交给一个人（收集起来）
Reduce    → 大家把东西交给一个人，路上顺便做加法
All 前缀  → 不是只交给一个人，而是所有人最终都得到相同的结果

AllGather      = 大家都得到完整数据（人手一份拼好的）
AllReduce      = 大家都得到求和结果（人手一份算好的）
Reduce-Scatter = 先求和，再切片，每人只拿自己那一段
```

> 补充校正：口语中容易把 AllGather 说成"All-scatter"，两者方向相反——Scatter 是把完整数据"发出去"（切片），Gather/AllGather 是把切片数据"收回来"（拼完整），注意不要混淆。

### 7.6 底层是怎么实现的：Ring 算法详解

前面讲的都是"输入输出长什么样"（逻辑语义），但 NCCL 底层到底是怎么把数据从 A 传到 B 的？这决定了通信要花多长时间、为什么大模型训练卡间要用 NVLink。最经典、最重要的实现是 **Ring（环形）算法**。

#### 7.6.1 朴素实现 vs Ring 实现

最笨的 AllReduce 实现：找一个"中心节点"，所有人把数据发给它，它算完再广播回去（Reduce + Broadcast）。

```
问题：中心节点 GPU0 要接收 N-1 份完整数据、再发送 N-1 份完整数据
      → 中心节点的带宽是瓶颈，通信量随 N 线性增长，N 越大越慢
```

Ring 算法把所有 GPU 连成一个逻辑环，不设中心节点，每个人只跟左右邻居通信，带宽压力均摊到每一条链路上：

```
      ┌──────────────────────────────┐
      ↓                              │
   GPU0 ──→ GPU1 ──→ GPU2 ──→ GPU3 ──┘
   （每张卡只对下一张卡发送，只从上一张卡接收）
```

#### 7.6.2 Ring Reduce-Scatter：一步步图解

假设 4 张卡，每张卡的梯度向量都被切成 4 段（段数 = 卡数）：

```
初始状态（每张卡都有完整梯度，但内容不同）：
GPU0: [a0, a1, a2, a3]
GPU1: [b0, b1, b2, b3]
GPU2: [c0, c1, c2, c3]
GPU3: [d0, d1, d2, d3]
```

Ring Reduce-Scatter 分 **N-1 步**（这里 N=4，走 3 步），每一步每张卡都把"自己当前持有的某一段"发给下一张卡，同时接收上一张卡发来的段并累加：

```
第1步：GPU_i 把第 i 段发给右邻居，累加收到的段
GPU0: 段0(a0)      → 发给 GPU1
GPU1: 段1(b1)      → 发给 GPU2
GPU2: 段2(c2)      → 发给 GPU3
GPU3: 段3(d3)      → 发给 GPU0

累加后：
GPU0 收到 d3，持有段3 = d3+a3
GPU1 收到 a0，持有段0 = a0+b0
GPU2 收到 b1，持有段1 = b1+c1
GPU3 收到 c2，持有段2 = c2+d2

第2步：继续把"刚更新出来的段"往右传，继续累加
GPU0(段3=d3+a3) → 发给GPU1 → GPU1的段3 = d3+a3+... 
（依此类推，每一步累加范围多覆盖一张卡）

第3步（最后一步，共 N-1=3 步）：
每张卡上都有且只有一段，是全部 4 张卡在这一段上的完整总和：
GPU0: 只有段3 = a3+b3+c3+d3  ✅ 完整
GPU1: 只有段0 = a0+b0+c0+d0  ✅ 完整
GPU2: 只有段1 = a1+b1+c1+d1  ✅ 完整
GPU3: 只有段2 = a2+b2+c2+d2  ✅ 完整
```

这正好就是 7.2 节里 Reduce-Scatter 的最终效果——每人只拿到自己那一段的求和结果，只是这里揭示了"怎么一步步传出来的"。

#### 7.6.3 Ring AllGather：接着再走 N-1 步

Reduce-Scatter 结束后，每张卡只有 1/N 的完整数据。AllGather 用完全相同的环形传递方式，只是**不再做加法，只是转发**，再走 N-1 步，把缺的那几段依次传到每张卡：

```
第1步：GPU0(有段3) 把段3发给 GPU1 → GPU1 现在有 段0、段3
第2步：GPU1 把刚收到的段3 转发给 GPU2 → GPU2 现在有 段1、段2、段3
第3步：GPU2 转发段3给 GPU3 → GPU3 现在有 段2、段3、段0(...)
（同时其余方向的段也在环上同步转发）

3 步之后，每张卡都集齐了 4 段 → 拼成完整梯度
GPU0/1/2/3: [段0, 段1, 段2, 段3] 全部一致
```

所以 **AllReduce = Reduce-Scatter（N-1步）+ AllGather（N-1步） = 共 2(N-1) 步**，这与 7.3 节的逻辑关系完全对应，只是这里精确到了"具体走几步"。

#### 7.6.4 为什么 Ring 算法是带宽最优的

关键结论：**每一步，每张卡发送和接收的数据量都只有 (总数据量/N)，与卡数 N 无关！**

```
单卡总通信量 = 2(N-1) 步 × (数据量/N) ≈ 2 × 数据量（当 N 较大时）

对比朴素中心化实现：
中心节点通信量 = (N-1) × 数据量  → 随 N 线性暴涨，N=64 时中心节点要扛 63 倍数据量

Ring 算法：
每张卡通信量恒定 ≈ 2 × 数据量，与卡数无关（GPU 越多，均摊后单卡负担不变）
→ 这就是大规模分布式训练能横向扩展（scale out）的数学基础
```

这也解释了两个常见现象：
- **为什么 AllReduce 的耗时约等于"传输 2 份完整梯度"的时间**，而不是 N 份——因为环形算法把总传输量摊薄了。
- **为什么卡间带宽（NVLink/IB）比卡数更重要**：数据要在环上转 2(N-1) 跳，每一跳都要走一次物理链路，链路带宽越低，总延迟越高；这也是 TP（需要频繁 AllReduce）必须挤在单机 NVLink 内、不能跨机器的根本原因（对应 4.3 节）。

#### 7.6.5 结合 ZeRO 例子：通信量到底省在哪

回到之前讨论的 ZeRO-1/2 例子（4 卡，每卡梯度 4 段）：

```
ZeRO-1（只切分优化器状态）：
  梯度同步：完整 AllReduce = Reduce-Scatter(3步) + AllGather(3步)，共 6 步
  参数更新后：额外 1 次 AllGather 同步更新后的参数（因为优化器状态是分片的）
  → 通信量：≈ 2 份梯度 + 1 份参数

ZeRO-2（切分梯度 + 优化器状态）：
  梯度同步：只做 Reduce-Scatter(3步)，到此为止，不做后面的 AllGather
  → 每张卡只保留 1/4 梯度，省下一半梯度显存
  参数更新后：同样需要 1 次 AllGather 同步参数
  → 通信量：≈ 1 份梯度 + 1 份参数（比 ZeRO-1 少了近一半梯度通信量所对应的"完整驻留"，
     但注意：Reduce-Scatter 本身的通信量和 AllReduce 的前半段几乎一样，
     ZeRO-2 省的主要是显存，通信总量相比 ZeRO-1 基本持平甚至略省，核心收益在显存而非通信）
```

> 常见误区澄清：ZeRO-1/2 相比朴素 DDP，**通信总量并没有增加**（AllReduce 本来就内部拆成 Reduce-Scatter+AllGather 两步走），ZeRO 只是在这两步之间"顺手"把结果按分片保留，从而省显存；额外增加的通信只有更新参数后那一次 AllGather（因为分片更新后的参数需要重新同步给所有卡）。

## 八、第 3 层：训练工具库（封装层）

### 8.1 Accelerate（HuggingFace）

定位：分布式训练的"适配器"。核心思想是写一份训练代码，自动适配 DDP / FSDP / DeepSpeed / TPU 等不同后端。


```python
from accelerate import Accelerator
accelerator = Accelerator()

model, optimizer, dataloader = accelerator.prepare(
    model, optimizer, dataloader
)
```

优点：上手简单，切换后端只需改配置文件，与 HuggingFace 生态无缝集成。


适合：中小规模模型（7B 以下）的对齐训练、快速实验。

### 8.3 verl

定位：字节跳动开源的、专为大规模 RLHF 设计的高性能框架。核心设计（HybridFlow 编程范式、异步 rollout-reward-optimize 流水线）详见 [verl.md](verl.md)。特点：训练用 Megatron/FSDP，推理（rollout）用 vLLM，两者解耦、各自用最适合的后端；显存效率高，适合工业级 RLHF。

## 九、推理侧：Attention 的几种实现方式（eager / SDPA / FlashAttention / PagedAttention）

训练侧关注"怎么把模型/数据切到多卡上"，推理侧还有一组同样重要但完全不同维度的优化：**同一个 Attention 数学公式，用不同的底层实现方式计算，速度和显存可以差几倍到十几倍**。这里的几种实现不是互相替代的并行策略，而是**同一个算子的不同实现后端（kernel）**。

### 9.1 Attention 的标准数学公式（先对齐基准）

$$\text{Attention}(Q,K,V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

不管用哪种实现方式，算出来的**数值结果都应该一致**（或在数值精度误差范围内一致），区别只在于**怎么算更快、更省显存**。

### 9.2 eager（朴素实现）

`eager` 是 HuggingFace Transformers 里 `attn_implementation="eager"` 对应的实现方式：直接按 PyTorch 算子逐步计算——`Q @ K.transpose(-1,-2)` → 除以 `sqrt(d_k)` → `softmax` → `@ V`，也就是本笔记 [手写Attention代码合集](基础代码/手写Attention代码合集.md) 中最基础的写法。

**问题**：中间会显式生成一个 `[seq_len, seq_len]` 的完整注意力分数矩阵（Attention Score Matrix），这个矩阵需要写入并从显存（HBM）中反复读写：

```
标准 Attention（eager）的问题：

每次 Attention 计算：
HBM → SRAM:  读取 Q, K, V              (大量 HBM 读)
SRAM → 计算: QK^T
SRAM → HBM:  写回 Attention Score 矩阵  (HBM 写，seq_len × seq_len 很大！)
HBM → SRAM:  再读 Score 矩阵            (HBM 读)
SRAM → 计算: Score × V
SRAM → HBM:  写回输出                  (HBM 写)

问题：中间结果反复在 HBM 和 SRAM 之间搬运
     序列越长，Score 矩阵越大（随 seq_len 平方增长）
     HBM 带宽成为瓶颈（Memory Bound，不是算力不够，是数据搬运太慢）
```

### 9.3 SDPA（`torch.nn.functional.scaled_dot_product_attention`）

**SDPA 不是某一种具体的加速算法，而是 PyTorch 官方提供的一个统一算子接口**，它会根据运行环境（硬件、精度、是否有 mask、序列长度等）自动在多种底层 kernel 之间选择最优实现，包括：

- **Math 后端**：等价于 eager 的朴素实现（数学上最直接，作为 fallback）
- **FlashAttention 后端**：满足条件时自动调用 FlashAttention 算法（见下）
- **Memory-Efficient Attention 后端**：类似 xFormers 提供的显存优化实现

```python
import torch.nn.functional as F

# 函数签名（PyTorch 官方）
output = F.scaled_dot_product_attention(
    query, key, value,
    attn_mask=None,
    dropout_p=0.0,
    is_causal=False,   # 因果 mask，用于自回归生成
    scale=None,        # 默认使用 1/sqrt(d_k)
    enable_gqa=False,  # 是否启用 Grouped Query Attention 加速路径
)
```

一句话理解：**SDPA 是接口，FlashAttention 是这个接口背后可能被调用的具体实现之一**。在 HuggingFace Transformers 里设置 `attn_implementation="sdpa"`，就是把 Attention 计算交给 PyTorch 自动选择最优后端，通常比 `eager` 快且省显存，且不需要额外安装第三方库。

### 9.4 FlashAttention（真正的算法创新）

FlashAttention 是 Stanford 团队提出的 Attention 精确计算加速算法（不是近似算法，数学结果完全等价），核心思路是用 **Tiling（分块）+ Online Softmax** 避免把完整的 Score 矩阵写入 HBM：

```
有 FlashAttention（Tiling 分块）：

核心思想：把 K、V 切成小块（Tile），每块都能装进 SRAM，在 SRAM 内完成计算

Step 1: Q 从 HBM 加载到 SRAM（只加载一次）
Step 2: 循环处理每个 KV Block：
        ┌──────────────────────────────────┐
        │  从 HBM 加载 KV Block_i 到 SRAM  │
        │  在 SRAM 内计算 Q × K_i^T        │
        │  在 SRAM 内做 Softmax（online）   │  ← 关键技巧：不需要提前知道全局最大值
        │  在 SRAM 内计算 × V_i            │
        │  累加到输出（不写回 HBM！）       │
        └──────────────────────────────────┘
Step 3: 最终输出写回 HBM（只写一次）

减少 HBM 读写次数 → 从 Memory Bound 变为 Compute Bound（真正发挥出 GPU 算力）
```

**Online Softmax** 是 FlashAttention 的关键数学技巧：标准 Softmax 需要先看到一整行的所有值才能算出最大值用于数值稳定（减去最大值防止溢出），FlashAttention 通过维护一个运行中的最大值和归一化因子，分块处理时增量更新之前的结果，从而不需要把整行数据都装进内存就能算出正确的 Softmax。

**性能数据**（来自 FlashAttention / FlashAttention-2 论文）：
- FlashAttention 在 A100 上相比标准实现有 **2~4 倍**的速度提升，序列越长优势越明显
- 由于不存储完整的中间注意力矩阵，显存占用可降低 **10~20 倍**
- FlashAttention-2 在 FlashAttention 基础上进一步提速 **2~3 倍**（主要通过减少非矩阵乘法运算、更好的并行划分实现）

### 9.5 eager / SDPA / FlashAttention 三者关系梳理

```
关系不是并列的三选一，而是"接口"与"实现"的分层关系：

┌─────────────────────────────────────────────┐
│  你的代码：model(input, attn_implementation=?)│
└─────────────────────────────────────────────┘
              ↓ 选择实现方式
   ┌──────────┼──────────────┐
   ↓          ↓              ↓
"eager"    "sdpa"      "flash_attention_2"
朴素实现   PyTorch统一接口   直接指定用 FlashAttention 库
   │          │              │
   │    自动选择最优后端：     │
   │    ├─ Math（≈eager）    │
   │    ├─ FlashAttention ───┤ ← 两条路径最终都可能落到同一个 kernel
   │    └─ Memory-Efficient  │
   ↓          ↓              ↓
结果数值一致，速度/显存差异巨大
```

在 HuggingFace Transformers 中，`attn_implementation` 参数可以显式指定为 `"eager"`、`"sdpa"` 或 `"flash_attention_2"`（后者需要额外 `pip install flash-attn`）；不指定时库会自动探测环境并选择可用的最优实现。

### 9.6 PagedAttention（vLLM，解决的是另一个维度的问题）

**容易混淆的点**：PagedAttention 和 FlashAttention 优化的**不是同一个环节**，两者是互补关系，不是竞争关系。

| 概念 | 作用层面 | 解决的问题 |
|------|---------|-----------|
| **FlashAttention** | 单次 Attention 计算内部，HBM ↔ SRAM 的数据搬运 | 计算时的显存带宽瓶颈（Memory Bound） |
| **PagedAttention** | 多个请求的 KV Cache 在 HBM 里怎么存放 | 显存碎片化、利用率低（推理服务场景） |

PagedAttention 借鉴操作系统虚拟内存分页的思想：把每个请求的 KV Cache 切成固定大小的 Block（默认 16 个 token 一块），Block 在物理显存中可以不连续存放，通过一张 Block Table 做逻辑地址到物理地址的映射：

```
逻辑视图（程序看到的）：
Request A: [Block0] → [Block1] → [Block2]   (逻辑连续)

物理视图（显存实际布局）：
┌──────┬──────┬──────┬──────┬──────┬──────┐
│Block2│Block0│Block5│Block1│Block3│Block4│
│(A)   │(B)   │(A)   │(A)   │(B)   │(C)   │
└──────┴──────┴──────┴──────┴──────┴──────┘
         ↑ 物理不连续，但通过 Block Table 找到它们
```

**需要澄清的两个常见误解**（vLLM 论文/资料中容易被误读的地方）：

1. ❌ "PagedAttention 按需加载部分 KV 数据参与计算" —— **不准确**。Decode 阶段虽然 Query 只有新生成的 1 个 token，但 Key/Value 仍然需要当前序列**全部历史 token** 的 KV Cache 参与计算，参与计算的数据量并没有减少。PagedAttention 解决的是这些 KV 数据"**怎么存**"（分页、非连续、按需分配 block），而不是"**存/算多少**"的问题。
2. ❌ "运行时动态调整 block 大小" —— **不准确**。Block Size 是启动时的静态配置超参数（vLLM 默认 16），运行期间不会改变；动态的部分只是**block 的分配数量**会随序列增长按需申请。

两者结合时的完整数据流：vLLM 按 Block Table 把物理上分散的 KV Block 依次从 HBM 搬到 SRAM，每次只搬一个 block（FlashAttention 式的分块思想），在 SRAM 内完成该 block 的 Attention 计算并累加结果，兼顾了"显存高效存储"（PagedAttention）和"计算高效搬运"（FlashAttention）两个维度。更完整的 GPU 架构（SM/HBM/SRAM/Warp 调度）视角，见 [VLLM.md · GPU 架构全景](../HuaggingFace/VLLM.md)。

### 9.7 GQA 与 Attention 实现方式的关系

[手写Attention代码合集 · MultiQueryAttention](基础代码/手写Attention代码合集.md#三multiqueryattention-mqa) 中介绍的 MQA/GQA 是**模型结构层面**的设计（减少 K/V 头数），而这一节讨论的 eager/SDPA/FlashAttention 是**同一个 Attention 结构的不同计算实现**，两者是正交的优化维度，可以叠加：比如一个用了 GQA 结构的模型，推理时依然可以选择用 SDPA 或 FlashAttention 后端来加速计算。

需要注意的是，PyTorch SDPA 对 GQA 的支持是有条件的：目前只在 CUDA 上的 FlashAttention 和 Math 后端支持 `enable_gqa=True`，且要求 Query 头数能被 Key/Value 头数整除。

### 9.8 一张表总结推理加速的几个层次

| 层次 | 涉及技术 | 解决的问题 |
|------|---------|-----------|
| 模型结构层 | MHA → GQA → MQA → MLA | 减少 K/V 头数或做低秩压缩，从根本上减小 KV Cache 体积 |
| 单次计算实现层 | eager → SDPA → FlashAttention | 减少 HBM 读写次数，把 Memory Bound 变成 Compute Bound |
| 多请求显存管理层 | PagedAttention | 解决多个并发请求的 KV Cache 碎片化、利用率低的问题 |
| 服务调度层 | Continuous Batching、Chunked Prefill | 提高 GPU 利用率，让 Prefill/Decode 请求高效混合执行 |

> 服务调度层的 Continuous Batching、Chunked Prefill 等内容详见 [vLLM参数与推理机制详解.md](vLLM参数与推理机制详解.md)。
